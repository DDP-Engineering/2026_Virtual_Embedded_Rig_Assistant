# ESP32 panic analysis

1. Load serial-monitor's console/identification skills, run `serial list`, and confirm the port, chip and baud. Never guess them. Capture with `run_program` program `serial`, args `["capture", "--port", "<confirmed-port>", "--duration", "10"]`. Add `--reset` only to reproduce an expected crash after explaining the reset. Keep the entire Guru Meditation message, exception cause, registers and `Backtrace:` line from the log. Use a bounded duration long enough to include the complete backtrace; stopping on `Guru Meditation` would truncate it. `idf.py monitor` is blocked.
2. Locate the **ELF from the exact build that was flashed**. Check the target and build metadata/binary identity with the user and build records. Do not rebuild over the only matching ELF before decoding. An unrelated, stripped or stale ELF produces misleading lines. If the match is unknown, say so and obtain it before claiming a source location.
3. Select `xtensa-addr2line` for ESP32/ESP32-S2/ESP32-S3, or `riscv-addr2line` for the RISC-V target confirmed by the project (for example C3/C6/H2). They detect EIM-installed `xtensa-esp-elf-addr2line` and `riscv32-esp-elf-addr2line`. Pass `args: ["-pfiaC", "-e", "build/<matching-app>.elf", "0x<PC>", "0x<next-PC>"]`. For Xtensa `PC:SP` backtrace pairs, decode the PC before each colon; do not pass stack pointers as instruction addresses. Decode the reported RISC-V exception PC and available call-stack instruction addresses using the corresponding tool.
4. Read the decoded source lines and callers. Correlate the exception type, register values and code path; distinguish a supported cause from a hypothesis. `??:0` or missing symbols is insufficient evidence. Report the original address, matching ELF, function and file:line, and preserve the raw log.
5. If the flashed build enabled core dump to flash and has a core dump partition, stop any background serial capture first. Use `idf.py` args `["-p", "<confirmed-port>", "coredump-info"]` from the matching project/build directory; for a non-default build directory use `-B` with its real path. This device-read operation can reset the board and follows the session approval mode. Inspect all task stacks from the result. A UART dump must be fully captured; consult the installed IDF version's core dump documentation for its file-input options rather than guessing flags. Interactive `coredump-debug`/GDB is not needed here.

Configuration changes belong in `sdkconfig.defaults`. After reconfigure, read the effective generated configuration and verify the desired core-dump values before build and an approved reflash for future captures. Defaults do not override already-set `sdkconfig` values; if those persist, agree on the project's supported regeneration workflow instead of silently discarding the existing configuration or resetting the target. Never edit `sdkconfig` directly. See [ESP-IDF configuration defaults](https://docs.espressif.com/projects/esp-idf/en/v5.4.3/esp32/api-guides/build-system.html#custom-sdkconfig-defaults). VERA detects the vendor toolchain; the user installs it through EIM. Fixtures or simulated backtraces do not prove a real-board diagnosis.
