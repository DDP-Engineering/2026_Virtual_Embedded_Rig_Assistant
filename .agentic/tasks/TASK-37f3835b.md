## Frame

Problem: VERA sizes cables and checks protective devices (PWR-02/03) but nothing proposes how a motor is started or
driven, sizes the starter assembly around it or gives a connection/interlock scheme for a panel adapter (OBSERVED:
00_Planning/plan/electrical-power.md lists PWR-04 planned; no motor engine in core/src/electrical/). The electrical
tool specs also overflow small-context models: PWR-03 had to give sessions/electrical-model.test.ts a 64k window
(OBSERVED: PWR-03 journal DEVIATION, test comment).
Desired outcome: (1) each plugin-specific electrical tool is offered only while its own plugin (by plugin id) is
loaded, the model tools while any electrical/automation plugin is loaded (STATED: coordinator STEP 1). (2) plugin
`motor-drives` (ecosystem electrical, pack "Electrical power and distribution") plus a pure engine in core and a
write tool that, per motor of the model, compares DOL, reversing, star-delta, softstarter and VFD against the process
function, the motor nameplate, the network, load torque/inertia, acceleration, starts/hour, environment, duty and
motor cable; proposes the simplest feasible method; sizes contactor/protection/overload relay, bypass and drive with
utilisation categories and cited derating; reports braking, EMC/dv-dt and protection needs only from applicable data;
and stores one PWR-00 result with input snapshots, calculations/curve points within the modelled domain, product codes
and a structured logical connection/interlock scheme for the future ECAD adapter (STATED: ticket PWR-04, brief).
Actors: the agent with motor-drives loaded; the engineer who keeps model, catalog and profile and approves result
writes; CAD-02 panel-engineering adapter reading the scheme (STATED: brief).
Primary scenario: after electrical_network and protection_coordination stored current results, the agent calls the
motor tool naming the protection run, a catalog and per motor the process requirements and candidate items; VERA
prepares result.json (approval like a write) with the comparison, the proposal, the assembly and its scheme; a later
change of the motor or its circuit makes the result stale.
Examples: a fan without a starting-current limit -> DOL; an 11 kW pump with a 400 V delta winding, 6 terminals and a
starting-current limit -> star-delta; a constant-torque conveyor with a 230/400 V motor (star at 400 V) -> star-delta
not eligible, softstarter fails torque, VFD proposed (INFERRED: physics of the methods; fixed as fixtures with hand
calculations).
Counterexamples: a VFD chosen by kW only; star-delta on a 3-terminal or star-operated motor; a passing acceleration
time without inertia or torque data (must be unknown/conditional); a written drive parameter or a claimed safety
function (STATED: ticket).
In scope: tool gating per plugin id; engine + write tool + request schema; motor/load property names; catalog
conventions for overload relays, softstarters and drives; optional structured `assemblies` in the result format 1;
generic report section for it; plugin package, skill, README, pack; en/ro/de/fr tool texts; cited fixture catalog;
fictional plant model with three motor loads; spec/requirements/knowledge/plan.
Out of scope: drive parameterisation or any device command (STATED: ticket); validated safety functions (STATED);
copied vendor catalogs/IEC tables (STATED: user decision); harmonics/PFC (PWR-05); ECAD drawing (CAD-02); motor
contribution to fault currents (PWR-02 limit).
Constraints: format 1, no migrations; reuse catalog selectItems/coordinationFor, PWR-03 stored verdicts, result-change,
generic report, one unit table; public pages read only in the built-in browser, no downloads; targeted tests; no
commit; no CHANGELOG (STATED: brief).
Success signals: PWR-04-A..D focused tests green on Windows and WSL2; lint, typecheck, check:i18n green; gating tests
updated and the 64k window removed if no longer needed.

## Design

**Approach**: like PWR-02/03, product code next to the model: pure engine `electrical/motor-drives.ts`
(`motorDrivesRequestSchema`, `analyzeMotorDrives(input)` -> ElectricalResult, exported `accelerationTime` integrator for
the hand-calculation tests) and write tool `electrical/motor-drives-tool.ts` (`motor_drives`, class write) that reads
the model, the named protection result and the network result it names (`readResultFile` + `resultFreshness`, refuses
missing/invalid/foreign/stale), the catalog, runs the engine and prepares ONE result through `prepareResultChange`.
Result format 1 gets an optional strict `assemblies` list (shared electrical-model.ts) rendered by the generic report.
Rejected: a second file per run for the scheme (result-change writes one file; CAD-02 reads one result); recomputing
protection verdicts (PWR-03 hand-over: read them); the ABB mean-torque formula as engine (it is the independent
reference); hard-coded trip-class or derating tables (they belong to the catalog with a citation).
Reuse: `selectItems` on a one-item sub-catalog for every cited comparison (contactor Ie per category, relay range and
band, softstarter/drive currents and derating bounds), item `accessories` for the interlock, PWR-03 stored criteria,
`result-change.ts`, `renderResultReport`, units.ts (new dimensions inertia kg·m², rate 1/h, frequency kHz, known
properties). Gating: `electricalPluginTools` + `electricalToolOffered` in tools.ts, `SessionHost.electricalPlugins`
(RULING-001).
**Interfaces and data**: spec REQ-DATA-79118f9a; fixtures `tests/fixtures/motor-drives/plant-m.json` (fictional
plant: 400 V Dyn11 transformer, MDB, fan 2.2 kW, pump 11 kW 400 V delta, conveyor 5.5 kW 230/400 V star) and
`cat-motor-drives.json` (GV2ME10, C10G20/C10G32, LC1D09P7/LC1D18P7 with fuse tables copied from the PWR-01/03
fixtures; new LRD21, LAD9V2, ATS22D32Q, ATV930U75N4 from se.com UK pages; class 10A band from se.com FAQ FA22893; all
read 2026-11-15). Errors: invalid request/catalog or refused result -> thrown, nothing prepared; data gaps -> criteria.
**Files and test seams**: core electrical/motor-drives.ts, motor-drives-tool.ts, result-change.ts (tool union),
report.ts, units.ts, tools.ts, tools/registry.ts, tools/changes.ts, index.ts; shared electrical-model.ts, tools.ts,
events.ts, session-state.ts; tests motor-drives.test.ts (fixture pipeline network -> protection -> motor, hand calcs,
ABB example, synthetic edits), motor-drives-tool.test.ts, results.test.ts, registry and session tests; desktop
workbench-tools.tsx + 4 locales; plugins/motor-drives/, catalog.yaml, packs.yaml; CONTRIBUTING, knowledge, plan.
**Risks and open decisions**: public pages give no softstarter starts/hour, no ATV930 EMC category or motor cable
length, no GV2ME trip class: those criteria stay unknown with real data; the switch-over transient of star-delta and
the softstarter current-speed curve are not modelled (stated limits); WSL is not native Ubuntu.
**Requirement map**: DATA-79118f9a, FUNC-30561076, 270a3c8e, 31a5706e, 179328ee, 12507326, f19b1719, 028689c0 ->
motor-drives.ts; REL-6bf4730e, FUNC-285949c8 -> motor-drives-tool.ts; DATA-e3d5c15f -> electrical-model.ts + report.ts;
TEST-c04129a0 -> fixtures + motor-drives.test.ts; SEC-4dfa2a5b -> tools.ts + service.ts + desktop sessions.ts;
UX-d32cc9db -> locales.
