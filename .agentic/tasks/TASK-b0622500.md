## Frame

Problem: VERA cannot reach Bluetooth Low Energy devices. OBSERVED: no plugin under `05_Software/plugins/` imports a
BLE library; LAB-01's lease registry (`shared/src/lab-resources.ts`) knows the identity kinds `visa` and `bus-adapter`
only, and the runner's argv-derived leases cover `serial:` and `volume:` keys (`core/src/plugins/runner.ts`).

Desired outcome (STATED ticket IOT-06 and the coordinator's brief):
- An official plugin `ble-tools` with a pinned stable Bleak in a PEP 723 helper and the operations bounded scan,
  identify, discover-services, read-characteristic, subscribe-notifications, write-characteristic and report.
- A device is selected by identity plus a profile, never by public name or RSSI alone; addresses may vary and an
  advertisement resemblance never claims authentication. The profile declares service/characteristic UUIDs, payload
  type, byte order, units, limits, allowed operations and whether pairing is required.
- A standard UUID or a read property does not prove absence of effects; writes may control hardware and are
  classified by semantics; no arbitrary raw write and no firmware-update command.
- Adapter, connection and resource, notifications, MTU/fragmentation and backpressure are managed; pairing that needs
  UI is handed to the user, no automatic PIN attempts, no disabling of authentication; global Bluetooth configuration
  is never changed and no unrequested device is unpaired.
- The adapter/connection is reserved through LAB-01's one lease registry (STATED brief: follow IOT-04's kind and
  IOT-03's key; no second registry). Results `format: 1` under `arduino-iot-results/<run-id>/` keep UUID, raw payload,
  receive time and interpretation schema (STATED plan §3).

Actors: the user (declares the device in `lab/resources.json`, writes the profile, pairs a device through the OS when
the profile needs it, approves runs), the agent (runs `ble-tool`), VERA's program tools, approval gate, runner and
lease folder, the OS Bluetooth stack (WinRT on Windows, BlueZ on Linux) through Bleak, and the BLE device.

Primary scenario: the user declares `{"alias": "thermo", "kind": "ble-device", "address": "<address>", "profile":
"<profile id>"}` in `lab/resources.json` and a profile file listing the device's service, a temperature
characteristic (sint16 little endian, 0.01 °C, limits, read+notify) and a setpoint characteristic (write, class
configure, limits). The agent scans for 10 s (two advertisers with the same name are listed separately by address),
identifies `thermo` (address seen, profile services and properties match), reads the temperature five times,
subscribes for 30 s and, after approval as device-write, writes one setpoint value once.

Examples: STATED T06-A...T06-F. T06-A: the scan is bounded and two devices with the same name are not confused; an
unconfirmed target receives no write. T06-C: UUIDs, properties and payload schema are validated; a truncated value or
an unknown unit never becomes a fabricated measurement. T06-D: required pairing, absent adapter, timeout, disconnect
and reconnect leave no active subscription and no automatically re-sent command. T06-E: Stop and a disabled plugin
release managed connections; a lease conflict and a notification flood are handled. Example needing a value the user
has not given: the device's `<address>` and its profile UUIDs.

Counterexamples: STATED - no Bluetooth Classic, no peripheral/advertising server, no DFU, no universal pairing, no
raw arbitrary write, no automatic PIN, no change of global Bluetooth configuration, no selection by name or RSSI alone.

In scope: the package (manifest, README, skills, example profile, PEP 723 helper `ble-tool` with a support package),
catalog and pack entries; a registry identity kind `ble-device` in `lab-resources.ts` (as IOT-04 added `bus-adapter`);
a scpi/bus registry reader adjustment if their helpers refuse unknown kinds (INFERRED from IOT-04's hand-over, which
had to teach scpi to skip `bus-adapter`); offline tests with a fake Bleak; one bounded passive scan on this machine's
own adapter (STATED brief: OK); AEGIS records, knowledge, the plan row.

Out of scope: connecting to, pairing with or writing to any real BLE device without asking the user (STATED brief);
Bluetooth Classic, advertising, DFU (STATED); macOS/Android backends (INFERRED: targets are Windows x64 and native
Ubuntu x64, plan §4); native Ubuntu/BlueZ proof on this machine (STATED brief: open blocker).

Constraints: no commit/push; LF files; exact pins; formats stay 1; reuse the sibling plugin pattern and LAB-01's
registry; good enough over perfect, 1-2 review rounds, focused tests (STATED brief, memory).

Success signals: T06-A, C, D, E software parts shown by focused tests against a fake Bleak and the real runner with a
lease folder; a real passive scan on this machine passes; typecheck, lint, check:i18n green; plan row 6 built.

Evidence: OBSERVED bleak 3.1.0 wheel (pip download into the scratchpad): Requires-Python >=3.10, classifiers Windows 11
and Linux, WinRT deps `winrt-*>=3.1`, Linux `dbus-fast>=4.0.0`; BlueZ backend refuses BlueZ < 5.55
(`bluezdbus/client.py`) and passive scanning without `or_patterns` and without BlueZ >= 5.56 `--experimental`
(`bluezdbus/scanner.py`, `manager.py`); `BleakGATTProtocolError.code` (3.0+), `BleakBluetoothNotAvailableError.reason`
(NO_BLUETOOTH, POWERED_OFF, DENIED_*), `BleakClient(pair=False)` default, `write_gatt_char(response=)`,
`max_write_without_response_size`, `mtu_size`. OBSERVED `plugins/bus-tools`, `plugins/mqtt-tools`, the IOT-04/05
hand-overs, `resource-registry.ts` and `program-tools.ts` lease().

Assumptions: the device uses a public or static random address (INFERRED: resolvable private addresses are resolved
only by a bonded OS stack).

Unknowns: whether reading an encrypted characteristic of an unpaired device makes Windows show a pairing prompt by
itself (UNKNOWN; no fixture); whether BlueZ keeps a connection after the helper process is killed (UNKNOWN on this
machine); which real BLE device the user owns (UNKNOWN; none is known, so T06-B and real pairing stay open).

Decision-blocking questions: none. The brief fixes scope, registry reuse and the hardware boundary.

Proposed behaviors (not accepted until specify):
- Registry kind `ble-device` {alias, address, addressType, profile, adapter?, note?} keyed `ble:<address>`; the
  manifest's `resources {option: --device, kinds: [ble-device]}` brings LAB-01's lease, stop and cleanup.
- Identity: address seen in a bounded scan + profile services/characteristics/properties match = confirmed; an
  advertisement match alone = candidate; writes only to a confirmed target.
- Writes are named operations of the profile with a class (configure, actuate, persistent); persistent needs
  `--persistent` and is irreversible; a write is sent once and never retried; payload must fit one ATT write.
- Passive scanning by default; on Linux only `--active` (passive needs global BlueZ configuration).

## Design

**Approach**: a new official plugin `ble-tools` in the sibling pattern (bus-tools, mqtt-tools): plugin.yaml with one
PEP 723 program `ble-tool` (bleak 3.1.0 and its platform dependencies pinned with markers), skills, README, an example
profile. The device is a LAB-01 registry entry of a new identity kind `ble-device` (REQ-DATA-bc2b27d1), the extension
point the registry spec foresees and IOT-04 used; the manifest's `resources {option: --device, kinds: [ble-device],
grace: 5, cleanup: [release], cleanupTimeout: 30}` gives the cross-process lease, stop request and cleanup with no core
or runner change (REQ-FUNC-0f792684). Rejected: an argv-derived `ble:` key in the runner like IOT-03's `volume:` - it
would need a runner change and lose the registry's approval hash and the per-unit serial. Each connected operation is one
`asyncio.run`: find by address (bounded), connect once with pair=False, GATT check and identity (REQ-SEC-14b13f88), the
operation, stop_notify, one disconnect; nothing retried (REQ-REL-4706f92a, REQ-REL-1b62b28c).

**Interfaces and data**: spec REQ-DATA-e8502710 fixes the operations, profile, registry fields, results, codes and exit
codes. Backend selection follows Bleak's own `get_default_backend()` (WinRT or BlueZ, else os-unsupported) plus a
Windows build >= 22000 check and an installed-version check (REQ-PLAT-638438cc). Lifecycle physical = the managed link
(REQ-DATA-73b3fb3d); `write.effect` is separate. Payload decode/encode is pure (payload.py) and keeps raw hex always
(REQ-DATA-c1bd7c16). Notifications go through a callback that only stamps and enqueues into a bounded queue; a writer
coroutine drains, rate-checks and bounds (REQ-FUNC-fe487751, REQ-REL-d832225a). ATT 0x05/0x08/0x0C/0x0F and WinRT
access-denied map to pairing-required (REQ-SEC-ae588c69).

**Files and test seams**: new `05_Software/plugins/ble-tools/` (plugin.yaml, README.md, skills/ble-devices and
skills/ble-profiles, profiles/bench-thermometer.json, scripts/ble_tool.py, scripts/ble_support/{__init__, cli, report,
workspace (byte-identical copy), lifecycle (copy of bus-tools'), registry, profile, payload, backend, scan, device,
notify, write, operations}.py); `shared/src/lab-resources.ts` (+ its test) for the kind and key; scpi
`registry.py` OTHER_KINDS (REQ-FUNC-de5e43b9); catalog.yaml official list + metadata and packs.yaml arduino group;
prepare-plugins test list. Tests: `tests/integration/ble-tools.test.ts` runs the helper on the toolchain Python with a
fake `bleak` package in `tests/fixtures/ble-tools/fake-bleak/` (bench JSON in FAKE_BLE_BENCH: backend, adapter state,
devices with advertisements, GATT tables, values, notification streams and faults; every call logged to FAKE_BLE_LOG;
connected state in FAKE_BLE_STATE so a cleanup run sees it) and the real ProgramRunner with a lease folder; an opt-in
block runs one real passive scan when VERA_TEST_BLE_PYTHON names a Python with the pinned Bleak (REQ-TEST-e7ad54bf).

**Risks and open decisions**: T06-B (real read/notify/write), real pairing behaviour of Windows on an encrypted
characteristic, BlueZ keeping a link after a killed helper, and native Ubuntu stay open blockers (no fixture, no Linux
host). On a bonded device a CCCD left enabled by a killed helper persists; the result reports subscription unknown.
Advertisement and GATT payloads are untrusted data; the skills say so.
