## Frame

Problem: Desktop main keeps a busy previous workbench runtime open in the background (PWB-01), but every
session IPC handler and the `vera:subscription` handler still go through the foreground runtime
(`sessions()` / `workbench()` in main/index.ts) (OBSERVED). A request naming a session of a background
workbench (stop, approval decision, snapshot, revision, subscribe) reaches the wrong SessionService and
fails NOT_FOUND, so a background turn cannot be stopped or its approval decided without bringing it to
the foreground (OBSERVED: index.ts session.* handlers; core SessionService.row throws NOT_FOUND for a
foreign session). `WorkbenchRuntimes.promote()` drops the subscriptions of the runtime leaving the
foreground (OBSERVED, RULING-005 of TASK-a49f4f0c). Session-event masking and session image identities use
the foreground workbench's config (OBSERVED: index.ts sessionContent, sessionImageIdentity). Live text
(message.delta, reasoning.delta, tool.update) is never stored, and a new subscription replays only
stored events, so a session reopened mid-stream shows no streamed text until message.done (OBSERVED: core
sessions/hub.ts subscribe/record). No main query exposes which sessions of which open workbench are running
or awaiting approval (OBSERVED: shared ipc.ts session channels).
Desired outcome: Session actions, snapshots and subscriptions reach the runtime that owns the session,
identified by stable workbench and session identities, whichever workbench is in the foreground. Stop,
approval decisions, tool execution, file writes and program cleanup stay bound to the originating
workbench, and mismatched or stale identities are refused. Event order and snapshot reconciliation hold
across session and workbench switches. Main exposes the scoped activity state the sidebar (#360) needs
(STATED: ticket #358 deliverables).
Actors: Desktop user switching workbenches and sessions; the renderer session view (useSessionEvents);
Desktop main IPC handlers; the future sidebar (#360) as a consumer of activity state.
Primary scenario: Start a turn in workbench A, open workbench B, start a turn in B. Both turns run in their
own runtime; A's approval or stop request reaches A while B is in the foreground; B's never touches A.
Returning to A shows A's streamed or final content (STATED: #358 done criteria).
Examples: (1) A awaits a write approval while B is in the foreground: `session.approval.decide` for A's
session approves in A, the write lands in A's folder, B's files are untouched. (2) `session.stop` for A's
session aborts A's turn only; B's turn completes. (3) Close B (foreground) while A runs: A completes.
(4) Reopen A mid-stream: `session.get` + subscribe sinceSeq yields every stored event once and the
current streamed text of the in-flight message. (5) Activity lists A (background, running) and B
(foreground, awaiting approval).
Counterexamples: A request naming a session that no open workbench holds (its workbench was released) is
refused, not sent to the foreground. A request that names workbench X but a session of workbench Y is
refused.
In scope: owner routing in Desktop main for every request that names a session (session.*, artifacts.list,
changes.list, subscribe/unsubscribe) and for session requests that name a workbench (session.list, sizes,
search, move, create, image.*); identity re-check at execution; owner-scoped event masking and image
identities; subscriptions kept with their owner across foreground changes; core live-text replay for new
subscribers; an activity query and change event for the sidebar; tests for the done criteria.
Out of scope: the app-wide concurrent-turn limit (#359) and the sidebar UI (#360) (STATED: brief, epic
#356). Document viewer, docs/index events, terminals and the Runs tab stay foreground-bound (OBSERVED:
DisplayDocuments, TerminalService current(), RunPresentation; RULING-006 of TASK-a49f4f0c). Requests keyed
only by artifact or change IDs (artifacts.open/reveal/export, changes.get) and download requests stay on the
foreground (INFERRED: the window shows only the foreground workbench's session content; no done criterion
needs them in the background). CLI (one workbench per process).
Constraints: master branch, no new branch, one local commit (STATED: brief). Formats stay at version 1, no
migrations or compatibility code (STATED). Core stays Electron-independent (OBSERVED: project.md). Targeted
tests only (STATED). Existing session request shapes keep working: about 95 e2e calls send session
requests without a workbench ID (OBSERVED: grep tests/e2e).
Success signals: Main replay test with two real runtimes: approval decided and stop applied in background
A while B is foreground, each write in its own folder, B's turn unaffected; close of one workbench leaves
the other's turn running; owner subscription survives the foreground change in order; a stale session
(released workbench) and a mismatched workbench ID are refused. Core hub test: a subscription opened
mid-stream receives stored events once plus the current live text, never live text of a finished message.
Activity query test. Native e2e: approval requested in background A is reviewed after returning to A.
Evidence: OBSERVED main/index.ts session handlers (lines ~1068-1296), vera:subscription handler,
emitAppEvent projection; main/sessions.ts subscription(), clearSubscriptions(); main/workbench-runtimes.ts
promote(); main/display-documents.ts (owner-keyed deterministic identities); main/display-identities.ts
(AES-GCM with owner in AAD); core sessions/hub.ts; core sessions/service.ts row(), stop(), update(),
recordRuntimeEvent(), approvals record; shared ipc.ts/events.ts; renderer hooks/use-session-events.ts
(snapshot + sinceSeq + 2 s revision heartbeat).
Assumptions: Session IDs are unique per creation (ULID); only a copied workbench folder (clone) carries the
same session IDs under the same workbench ID (INFERRED: database lives in <folder>/.vera/vera.db, PWB-01
e2e clone case).
Unknowns: How the sidebar (#360) will present background workbenches; the activity shape here is the
minimum it needs (UNKNOWN, decided by #360).
Decision-blocking questions: none (autopilot; defaults recorded as rulings).
Proposed behaviors: (accepted for autopilot, recorded as rulings) route by session ID with an optional
workbench ID check; foreground first when clones both hold a session; re-check the owner identity at
execution; keep owner subscriptions across foreground changes and drop them only when the owner is
released; replay the live text of in-flight items to a new subscriber; expose `session.activity` plus an
app event.

## Design

**Approach.** A new Desktop main `SessionRouter` (main/session-router.ts) over `runtimes.all()` (foreground
first) resolves the owner of each request: `session(sessionId, workbenchId?)` picks the open runtime whose
database holds the session (one indexed `SELECT 1 FROM sessions WHERE id=?` per runtime, statement cached
per handle), preferring one with the named ID (REQ-FUNC-038c9b9b, RULING-001); `workbench(workbenchId?)`
picks the open runtime with that ID, else the foreground (REQ-FUNC-eb591891). `run(route, op, prepare)`
calls the owner's `SessionsHost.run` with a guard that runs first in the queued slot and answers CONFLICT
unless the runtime still has the same workbench ID, folder and database handle (REQ-REL-6e1454c1,
RULING-002); the operation receives the owner's fresh snapshot for masking. Every index.ts handler that
names a session (session.*, artifacts.list, changes.list) and every workbench-scoped session handler moves
from `sessions()`/`workbench()` to the router; owner-dependent helpers become `sessionContent(owner)` and
`sessionImageIdentity(owner)` (REQ-SEC-a4fbf2c9). Rejected: a required workbench ID on every session
request (95 e2e and 33 renderer call sites, no extra safety over session-ID ownership plus the guard).
**Interfaces and data.** Errors: no runtime holds the session -> NOT_FOUND (REQ-REL-6ca70bd2); a named ID
that is not open or does not hold the session -> CONFLICT (REQ-SEC-cf233e14); changed runtime -> CONFLICT.
Subscriptions: the router authorizes the sender, routes subscribe to the owner host with the guard, sends
unsubscribe to every host (each drops only its own), and refuses a subscription ID another host holds.
`WorkbenchRuntimes.promote()` stops clearing subscriptions; drain on release and window reload still
clear them (REQ-FUNC-4f478637, RULING-003). Each runtime's SessionsHost gets its own `emit`, projecting
session events with that runtime's snapshot (agent masking, image identities); `emitAppEvent` keeps the
foreground projection for other topics. `DisplayDocuments.sessionImagePath(owner, path)` encodes for the
owner's ID and folder without switching its current owner; resolving stays foreground-only. Core
`SessionHub` keeps per-session live text (key type + messageId/callId, tail 500000 chars), drops entries
when the durable message.done / tool.done / turn.done / session.interrupted is recorded, and `subscribe`
replays rows, then a copy of the buffer taken before the listener was added, then queued re-entrant
events (REQ-FUNC-cbd535d1). Activity: core `SessionHost.onActivity(sessionId)` fires for turn.started,
turn.done, session.interrupted, approval.requested/decided and session.updated with a title or status;
SessionsHost forwards it as option `activity`; `WorkbenchRuntimes` option `changed` fires after each
lifecycle operation and settled release; index.ts emits app event `{type:"session.activity"}`
(REQ-FUNC-a6aa5e7c). `SessionsHost.activity()` lists top-level (non-delegated) sessions with status
running or awaiting_approval once the service is ready; channel `session.activity {} ->
[{workbenchId,name,folder,foreground,sessions:[{id,title,status}]}]` (REQ-FUNC-93ec5cc7). No stored format
changes.
**Files and test seams.** shared ipc.ts/events.ts (+ session-activity-ipc.test.ts); core sessions/hub.ts, service.ts
(+ hub/service tests); main session-router.ts (+ session-router.test.ts with scripted runtimes and
session-router.replay.test.ts with real WorkbenchService/SessionsHost + ReplayGateway: background approval,
stop, writes, subscriptions, activity), sessions.ts, workbench-runtimes.ts (+ test), display-documents.ts
(+ test), index.ts wiring; renderer mocks/mockApi.ts (activity); e2e tests/e2e/session-routing.spec.ts
(background approval reviewed after return, owner masking, activity, mismatch, streamed text after
resubscribe; stop and close isolation are proven in session-router.replay.test.ts).
**Risks and open decisions.** Clones holding the same session: foreground first, then retained order
(RULING-001). Display documents, docs/index events, terminals and the Runs tab stay foreground-bound;
artifacts.open/reveal/export, changes.get and downloads stay foreground (Frame out of scope). Background
index events are still dropped by DisplayDocuments (renderer subscribes only to the shown workbench). The
activity event carries no payload; #360 re-reads `session.activity`.
**Requirement map.** REQ-FUNC-038c9b9b router.session + run; REQ-FUNC-eb591891 router.workbench;
REQ-REL-6ca70bd2 NOT_FOUND in router.session; REQ-SEC-cf233e14 CONFLICT checks in router; REQ-REL-6e1454c1
guard in SessionsHost.run; REQ-FUNC-4f478637 router subscription + promote change; REQ-SEC-a4fbf2c9
per-runtime emit + owner masking + DisplayDocuments.sessionImagePath(owner); REQ-FUNC-cbd535d1 SessionHub
live buffer; REQ-FUNC-93ec5cc7 SessionsHost.activity + channel; REQ-FUNC-a6aa5e7c onActivity + registry
`changed` + app event.
