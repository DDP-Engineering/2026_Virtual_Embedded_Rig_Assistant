## Frame

Problem: VERA cannot build or upload native Arduino sketches. OBSERVED (`05_Software/plugins/`, catalog.yaml): no
plugin wraps arduino-cli; serial-monitor, esp32-esptool, microchip-pymcuprog and stm32-cubeprog cover other tools.
OBSERVED (`runner.ts` `start`): the serial-port guard refuses only ports named by *background* runs of the same
process, so two foreground runs on one port (two sessions uploading, or an upload while another session's foreground
capture runs) both start. OBSERVED (`git log feature/101-embedded-lab`, `_lab` worktree status): LAB-01's
resource/lease registry is not committed (its task TASK-a5a839c7 is at specify, uncommitted).

Desired outcome:
- An official plugin `arduino-cli` (STATED ticket IOT-01: manifest, helper with inspect/boards/cores/libraries/
  compile/upload/report, skills for compile diagnostics, library choice and test sketches) whose helper
  `arduino-tool` is the only way the agent reaches arduino-cli; arduino-cli itself is pinned (STATED: "Arduino CLI
  stabil pin-uit"; OBSERVED GitHub release v1.6.0 of 2026-11-10 with SHA-256 digests).
- Cores and libraries are installed with explicit versions into a VERA-owned Arduino environment, never the user's
  Arduino IDE folders (STATED); installing is its own operation, never a side effect of analysis (STATED).
- Compile and upload are separate (STATED): compile writes a run folder under `arduino-iot-results/<run-id>/`
  (STATED plan section 3) with the copied sources, binaries, declared flash/RAM, resolved libraries, core, hashes and
  logs; upload takes that run's verified binary only and refuses when the binary or the sketch changed (STATED T01-C).
- The target identity is FQBN with options, port, protocol and programmer when needed (STATED); the board on the port
  is identified before upload, and an unknown board or a common USB bridge never selects a model (STATED).
- Ports in use by another VERA run give BUSY (STATED T01-D), foreground runs included.

Actors: the user (approves installs, compiles and uploads), the agent (runs `arduino-tool`), VERA's runner and approval
gate, arduino-cli and the installed core's tools, the board.

Primary scenario: the agent installs `arduino:avr@1.8.8` and nothing else; inspects a sketch; compiles it for
`arduino:avr:uno` into a new run folder (flash/RAM, libraries, core, hashes); lists boards and picks the port whose
identity the user confirms; uploads that run's binary to the port (approval names the result file, VERA binds its hash);
reads the fixture's version banner with serial-monitor.

Examples: STATED T01-A...T01-F (ticket). T01-B: compiling for `arduino:avr:unoo` is refused with a diagnostic and no
upload; a missing library is a diagnostic, never an automatic install. T01-C: editing the sketch after compile makes the
upload refuse with a conflict. T01-D: a background serial capture on COM5 makes an upload to COM5 BUSY.

Counterexamples: STATED - no Arduino Runtime/Firmata/VERA Bridge, no conversion to PlatformIO, no daemon, no
interactive monitor, no burn-bootloader/fuses, no OTA, no direct pin commands; the helper never installs a missing
core or library during compile and never picks a board model from a USB bridge's VID/PID.

In scope: the package (manifest, README, three skills, helper with support package), pinned arduino-cli download and
PATH find, catalog/pack entries, fixture sketches, offline tests with a fake arduino-cli, real-tool tests gated on an
environment variable, the runner guard extension. INFERRED (ticket "identitate/resurse ... necesară") - the minimal
shared piece is the in-process port guard covering foreground runs plus Linux `/dev/serial/by-id` aliases; serial board
identity keys live in the helper.

Out of scope: STATED (ticket) daemon gRPC, interactive monitor, burn-bootloader/fuse, OTA, Runtime/Firmata, pin
commands; live debug (delegated to LAB-04). INFERRED (minimal shared infrastructure; LAB-01 owns it) - a cross-process
lease registry shared by desktop and CLI, manifest `resources`, cleanup supervisor.

Constraints: STATED (brief) downloads outside PyPI only with approval - granted 2026-11-13 for arduino-cli 1.6.0, the
package/library indexes, arduino:avr and arduino:samd; no board writes without approval; no commit/push/branch switch;
formats stay `format: 1`; modern minimum versions; UI texts en/ro/de; focused tests only. Branch
`feature/113-arduino-iot` (not the default branch).

Success signals: T01-A real compiles of AVR and SAMD fixtures on Windows with traceable core/libraries/config/binary;
T01-B/E/F covered by offline tests (fake arduino-cli, real runner) and real-tool runs; T01-C/D software parts (hash
conflict, BUSY, identity refusals) covered offline; real upload, serial readback, two-board and native-Ubuntu proofs

## Design

Diagrams: [diagram_TASK-239a7379.md](diagram_TASK-239a7379.md)

**Approach.** A new official package `05_Software/plugins/arduino-cli/` mirrors ngspice/kicad: a find-or-download
program `arduino-cli` (1.6.0 pinned, `preferDownload`, every direct command blocked - REQ-FUNC-5b49327c) and a
standard-library PEP 723 script `arduino-tool` with `uses: [arduino-cli]`, so the run receives
`VERA_PROGRAM_ARDUINO_CLI`. The helper owns all Arduino semantics; VERA core changes only in the runner's serial guard
(REQ-SEC-016c9aad, REQ-FUNC-868fc8ab). Rejected: wrapping arduino-cli directly with option-role classification (as git/
tshark) - its default configuration reads and writes the Arduino IDE's folders and `compile` may install profile
platforms, so isolation must be enforced in a helper (REQ-FUNC-32924acc). Rejected: sketch.yaml profiles as the version
pin - a profile build installs missing platforms on the fly (OBSERVED sketch-project-file.md), i.e. a hidden install;
the helper copies the sketch without sketch.yaml and pins versions through `install`/`--core`/`--library`
(REQ-FUNC-9fceeea6, REQ-REL-c731bd06, REQ-SEC-37d5b2a2). Shared infrastructure: no lease registry (LAB-01 not
committed); identity keys stay in the helper (`boards.py`), BUSY stays in the existing in-process guard.

**Interfaces and data.** CLI, environment layout, configurations, identity keys and the result format: spec
REQ-DATA-e444904d. Environment root `$VERA_ARDUINO_HOME` (tests) or `~/.vera-arduino`; offline configuration with a
dead loopback proxy for everything but `install` (verified with arduino-cli 1.6.0: `core update-index` fails in
0.2 s, compile and board list succeed). Compile works on `<run>/sketch/<name>` and `<run>/libraries/*` copies with the
build folder in `staging/<run-id>`; upload re-hashes, copies `<run>/binary` to staging and uploads that copy
(REQ-FUNC-f2b3eb7d, REQ-SEC-ea1a5b7d). VERA's approval binds `--build <run>/result.json` by hash; the helper binds the
binaries and sources through the hashes inside it. Errors: exit 2 with `errors[]` codes before arduino-cli acts, exit 3
with status fail/error after. Stop is the runner's tree kill; staging folders carry `owner.json` and `clean` removes
those whose owner process has ended (REQ-REL-fa13ca61).

**Files and test seams.** `plugin.yaml`, `README.md`, `scripts/arduino_tool.py`, `scripts/arduino_support/`
{`__init__`, `cli`, `environment`, `sketch`, `boards`, `compile`, `upload`, `report`, `workspace` (byte-identical copy
of ngspice's path rules)}, `skills/{arduino-build-fix,arduino-libraries,arduino-test-sketch}/SKILL.md`; catalog.yaml,
packs.yaml; `runner.ts` (+ `runner.test.ts`). Tests: `tests/integration/arduino-cli.test.ts` (manifest, catalog,
classification, every operation against `tests/support/fake-arduino-cli.py` launched through a generated wrapper,
real-runner Stop, gated real-tool compiles) with fixtures `tests/fixtures/arduino-cli/` (sketches VeraBlink,
VeraLibrary + libraries/VeraCounter, VeraBroken, VeraMissingLib, VeraMisnamed; fake scenarios).

**Risks and open decisions.** Cross-process BUSY (desktop and CLI on one port) stays open for LAB-01's lease
registry; at the merge LAB-01's registry replaces the guard extension and adopts the helper's serial identity kind.
USB port properties (vid/pid/serialNumber, matching_boards) are unverified on real hardware (no board). One version per
platform lives in the environment: a request for another version is refused, not swapped. Board list starts the
installed discovery tools, which also browse mDNS on the local network; network ports are ignored.

**Requirement map.** DATA-e444904d: cli/report/workspace + spec. FUNC-5b49327c: plugin.yaml. FUNC-32924acc:
environment.py configs. FUNC-9fceeea6: cli install. REL-c731bd06, SEC-f5477b64, SEC-8faa1e1d, SEC-37d5b2a2,
FUNC-6678cab1, REL-6b92ea2f: compile.py pre-checks and result. FUNC-d02a9d01: sketch.py. FUNC-cbd22972, FUNC-91c2c9a8:
boards.py. FUNC-f2b3eb7d, SEC-ea1a5b7d, SEC-77af299d, FUNC-165776d6: upload.py. SEC-016c9aad, FUNC-868fc8ab: runner.ts.
REL-fa13ca61: environment staging/clean + real-runner test. FUNC-e2eea361: report.py. SEC-93d5fc98: rules + argparse
surface. FUNC-693a8fbf: catalog/packs/skills. TEST-de25fd47: gated tests.
