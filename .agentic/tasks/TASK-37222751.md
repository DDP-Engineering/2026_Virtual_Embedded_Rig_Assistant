## Frame

Problem: The New Workbench page mixes creating with opening. It shows an "Open an existing one" panel and a Recent list that repeat the sidebar (OBSERVED: renderer/components/workbench.tsx 241-310; workbench-navigation.tsx covers open, missing state and remove). It only collects a name and a folder (OBSERVED: workbench.create request `{folder,name}`, shared/src/ipc.ts 342-346). Configuration is available only afterwards, in the modal WorkbenchEditor (OBSERVED: workbench-editor.tsx).
Desired outcome: New Workbench is a creation page. The engineer chooses a folder and sees the workbench configuration sections (general, documents, instructions, agent, tools, skills, indexing, plugins). Create writes the chosen configuration and instructions. Editing an existing workbench uses the same sections on a full page instead of a modal dialog (STATED: parent TASK-581e6591 RULING-001; user request "sa apara setarile de workbench cu selectie tool-uri, skill-uri, editare md ...").
Actors: the embedded engineer using the desktop app.
Primary scenario: Sidebar New Workbench → Choose folder → the name fills with the folder name if empty → adjust sections → Create → the overview of the new workbench opens.
Examples: Folder `D:\bench\stm32-g4` with an empty name → name becomes "stm32-g4". The engineer unchecks the `web_search` tool and edits the Device under test section, then clicks Create → workbench.yaml has `tools.disabled: [web_search]` and WORKBENCH.md has the edited text. A folder that already contains .vera/workbench.yaml → the page says it is already a workbench and offers Open.
Counterexamples: choosing a folder after typing a name keeps the typed name. A folder that has a .vera/WORKBENCH.md but no workbench.yaml → creation keeps the existing WORKBENCH.md (non-destructive creation, REQ-FUNC-adf92ecb).
In scope: create-only New page; folder inspection channel; create with initial configuration and instructions; draft skills selection at creation; a shared configuration form for create and edit; full-page editor; removal of Open/Recent from the New page, with tests moved to the sidebar; mock API, en/ro/de strings.
Out of scope: documentation folder autodetection, the Add folder picker and indexing preview or progress (child 2); retrieval settings (child 3); office formats (child 4) (STATED: parent In scope). Plugin backends (OBSERVED: placeholder).
Constraints: core remains Electron-agnostic; renderer access goes through shared validated IPC (OBSERVED: project.md). Non-destructive creation is retained (REQ-FUNC-adf92ecb). The CLI also composes WorkbenchService.create (OBSERVED: apps/cli). No compatibility paths for earlier development layouts (STATED: AGENTS.md). Implementation is on master, the repository default branch, as AGENTS.md directs.
Success signals: native e2e creates a workbench with edited tools, skills and instructions, and the files on disk reflect them; the New page has no open-workbench or open-recent controls; an existing-workbench folder offers Open; the editor renders as a page with the same sections.

## Design

**Approach.** Split the creation and editing UI around one controlled `WorkbenchConfigForm` (section nav + section content). It takes `config`/`setConfig`, `instructions`/`setInstructions` and a `skills` slot. Create mode passes a draft checkbox list built from inspection results. Edit mode passes the existing `SkillSettings`, which still saves immediately (REQ-UX-7f289a2c, REQ-UX-1d6c940b). The new `WorkbenchCreate` page owns the folder, name, inspection and draft state, and calls `workbench.create` once (REQ-UX-2c674629, REQ-FUNC-3815bacc). `WorkbenchEditor` becomes an inline page in `page-content`, replacing the modal `<dialog>`. Escape returns to the overview and restores focus to the element that opened it (REQ-UX-1d6c940b). `Workbench` keeps the active overview only. Rejected: a multi-step wizard (parent RULING-001).

**Interfaces and data.**
- `workbench.inspect {folder}` → `{folder, name, existing, instructions: string|null, skills: SkillSummary[]}` (REQ-FUNC-81ce68df).
  - Core `WorkbenchService.inspect(input)` resolves `folder()` (INVALID for relative paths, NOT_FOUND for missing ones). It reads WORKBENCH.md only when it is an ordinary file and lists skills with `SkillCatalog({root, userData, disabled: () => []})`. It performs no writes and runs serialized through `run`.
- `workbench.create {folder, name, config?, instructions?}`.
  - `config` is `workbenchPatchSchema.omit({name})`.
  - Core `create(input, name, initial?)` builds `mergeWorkbench(defaults, initial.config)` before `prepare`. Zod failures map to `veraError("INVALID")`, so no file is written (REQ-FUNC-38107da8).
  - WORKBENCH.md is written exclusively with `initial.instructions ?? pinnedTemplate(name)`. EEXIST keeps the file (REQ-FUNC-3815bacc, REQ-FUNC-adf92ecb).
  - The CLI's two-argument call is unchanged.
- Create mode prefill: name = inspect.name only if the field is empty (REQ-UX-56c8cefc). Instructions = inspect.instructions ?? template. When inspect.instructions exists, the Instructions section shows it read-only with a "kept" note, since creation never overwrites it.

**Files and test seams.**
- shared `ipc.ts`; core `workbench/service.ts` + `service.test.ts`; main `index.ts`.
- renderer: `workbench-config-form.tsx` (new), `workbench-create.tsx` (new), `workbench-editor.tsx`, `workbench.tsx`, `App.tsx`, `styles.css`, `locales/{en,ro,de}.json`, `mocks/mockApi.ts` (+ `mockApi.test.ts`).
- e2e: `workbench.spec.ts` (create with config, existing offer, sidebar missing/remove) and `mock.spec.ts`. Specs using `open-recent` or the dialog switch to a shared helper in `tests/e2e/workbench-helpers.ts`.

**Risks and open decisions.**
- The broad e2e selector churn is mitigated by keeping the `#workbench-name`, `choose-create`, `create-workbench` and `data-project-*` selectors.
- Removing the modal changes focus handling, which is covered by REQ-UX-1d6c940b tests.
- No open product decisions.
