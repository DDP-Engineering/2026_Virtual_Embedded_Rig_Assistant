## Frame

Problem: VERA computes design currents, cable capacities and fault levels (PWR-02) and holds cited manufacturer
items (PWR-01), but nothing checks a fuse or breaker against them: breaking capacity, overload coordination, automatic
disconnection, let-through energy, selectivity/cascading and starter coordination are not evaluated (OBSERVED:
network.ts limits "Protective device selection, overload coordination (I2 <= 1.45 Iz), disconnection times and
selectivity are not evaluated here"; plan electrical-power.md lists PWR-03 planned).
Desired outcome: plugin `protection-coordination` (ecosystem electrical, pack "Electrical power and distribution") plus
a product engine in core that, for circuits of the model, evaluates candidate fuses and breakers from one industrial
catalog against the CURRENT stored electrical-network result and writes one PWR-00 result (input snapshots, method,
sources, conditions) with pass/fail/unknown/not-evaluated per criterion and per candidate; breaking capacity uses only
the capacity kind the profile asks for (Icu, Ics, Icn; fuses their rated breaking capacity) at the covered voltage;
time-current data are bands with conditions; selectivity, cascading and starter coordination come only from the
catalog's manufacturer coordination tables (STATED: ticket PWR-03, coordinator brief).
Actors: the agent with an electrical plugin loaded; the engineer who keeps model, catalog and normative profile and
approves result writes; PWR-04 (motor-drives) reading the protection result to build starters.
Primary scenario: after electrical_network stored a current result for network A, the agent calls the protection tool
naming the network run, the catalog, the breaking-capacity basis and, per circuit, candidate items, a setting for
adjustable devices and the required disconnection time from the profile; VERA prepares result.json (approval like a
write) and returns the report; later a cable length changes, the network result and the protection result list as
stale.
Examples: iC60N 3P C40 (Icu 10 kA at 380..415 V) on a board with Ik3max 16.15 kA fails breaking capacity, while GV2ME14
(Icu 100 kA at 400/415 V) passes; a gG 20 A fuse (I2 = 1.6 In = 32 A) on a cable with Iz 21 A fails I2 <= 1.45 Iz
(30.45 A); an MCB C16 with band 8 In +/- 20 % (upper edge 153.6 A) and a stated instantaneous time 0.1 s passes a
0.4 s disconnection when Ik1min >= 153.6 A (INFERRED: hand calculations, fixed in tests).
Counterexamples: Icn at 400 V is never used for an Icu basis or for a 230 V circuit; average operating curves without a
band, a missing magnetic tolerance or a missing operating time give unknown, never pass; two devices without a
manufacturer selectivity table are not-evaluated, never "selective by curve overlap"; a stale network result blocks the
run.
In scope: engine (pure) + write tool storing the result through the prepared-change flow, request schema, catalog
parameter names for breaking-capacity kinds, conventional tripping ratio, instantaneous band, trip-time points,
let-through energy, RCD type/sensitivity, coordination table kinds; units (A²s); plugin package + skill + README +
pack; tool texts en/ro/de/fr; fixture catalog typed from public pages (Acti9 iC60N, Eaton Bussmann C10G gG, TeSys
GV2ME/LC1D with their real fuse coordination tables, Schneider Electrical Installation Guide conventional currents);
spec/requirements/knowledge; rename the PWR-01 fixture's `breakingCapacity` (labelled Icu on se.com) to
`ultimateBreakingCapacity`.
Out of scope: online relay/protection settings or any hardware configuration (STATED: ticket); copying full
manufacturer selectivity/cascading or type-2 tables or IEC tables (STATED: user decision); graphic curve overlap
(STATED: ticket); earth-fault relays, MV protection, arc-flash, DC; changing the model or approved selections; motor
starter assembly (PWR-04).
Constraints: format 1, no migrations; one unit table; reuse catalog selection (`selectItems`, `coordinationFor`) and the
PWR-02 stored result (`readResultFile`, `resultFreshness`) and generic report; fixtures cited (URL, read date, table);
no downloads (LVED250601EN answered with a download, not retried); targeted tests; no commit.
Success signals: PWR-03-A, C and D focused tests green on Windows and WSL2, PWR-03-B as far as public tables allow (real LC1D fuse tables; selectivity and type-2 breaker tables with Iq stay open and are named); lint, typecheck, check:i18n green.

## Design

**Approach**: like PWR-01/02, product code next to the model: pure engine `electrical/protection.ts`
(`protectionRequestSchema`, `analyzeProtection(input)` -> ElectricalResult) and write tool
`electrical/protection-tool.ts` (`protection_coordination`, class write) that reads the model, the named network result
(`readResultFile` + `resultFreshness`, refuses missing/invalid/foreign/stale), the catalog (`readCatalogFile`) and the
cable table the network result names (`readCableTableFile`, sha prefix check -> k), runs the engine and prepares ONE new
result file. The prepare-and-commit code of network-tool is moved into a shared `electrical/result-change.ts`
(`newRunId`, `prepareResultChange`) used by both tools (no behavior change for electrical_network). Plugin package
`protection-coordination` (ecosystem electrical, no program) with skill `protection-selection`, README, catalog and
pack entry. Rejected: a Python helper (second unit table, PWR-04 could not call it); curve digitising (values read
from graphs would be extracted, never decisive); hard-coded IEC conventional factors or gate tables (licensed, and
per product they belong to the catalog with a citation).
Reuse: catalog `selectItems` for every firm comparison (voltage, breaking capacity, I2 ratio, I2t) on a one-item
sub-catalog so the PWR-01 coverage/conservative/unconfirmed rules decide; `findItems` for cited band points;
`coordinationFor` for selectivity, cascading and starter tables; PWR-02 stored result values (designCurrent,
ik3MaxStart, ik1MinEnd, currentCapacity, crossSection, nominalVoltage, cableTable); generic `renderResultReport`;
units via units.ts (new A²s dimension and known properties).
**Interfaces and data**: spec REQ-DATA-a5673202. Fixture `tests/fixtures/protection-coordination/cat-lv-protection.json`
(cited: Acti9 iC60N A9F74316/A9F74216/A9F74340 from se.com/ae, Eaton Bussmann C10G16/C10G20/C10G32 from eaton.com,
TeSys GV2ME14 and LC1D09P7/LC1D18P7 with their fuse coordination tables copied from the PWR-01 fixture,
conventional fusing/tripping ratios from Schneider's Electrical Installation Guide); PWR-01 fixture parameter
`breakingCapacity` renamed `ultimateBreakingCapacity` (se.com labels it Icu), with its tests, skill and spec.
Errors: invalid request/catalog/table or refused network result -> thrown, nothing prepared; data gaps -> criteria.
**Files and test seams**: core electrical/protection.ts, protection-tool.ts, result-change.ts, network-tool.ts,
units.ts, tools.ts (gate list), tools/registry.ts, tools/changes.ts, index.ts; shared tools.ts, events.ts,
session-state.ts; tests protection.test.ts (fixture + network A result + hand calcs + synthetic catalog edits),
protection-tool.test.ts (prepare/apply, stale, report), registry/electrical-model session tests; desktop
workbench-tools.tsx + 4 locales; plugins/protection-coordination/, catalog.yaml, packs.yaml; CONTRIBUTING,
knowledge, plan page.
**Risks and open decisions**: no public numeric instantaneous operating times, fuse gates, I2t or selectivity /
type-2 tables with Iq were reachable (downloads/licences): real-data criteria for them stay unknown/not-evaluated and
PWR-03-B stays partly open; WSL is not native Ubuntu.
**Requirement map**: DATA-a5673202 -> protection.ts schema + units.ts; FUNC-b65fb9ee, f24b4131, b9c2bc7d, 884410b3,
894dce2a, 870b4cdc, REL-8f88c502 -> protection.ts; REL-62b1aee8, FUNC-4dcdce2d -> protection-tool.ts +
result-change.ts; TEST-4ef52f14 -> fixture + protection.test.ts; SEC-4dfa2a5b -> electricalToolNames; UX-d32cc9db ->
locales.
