## Frame

Problem:
- STATED (user, 2026-10-31): electronics users keep several sources open (datasheets, Excel
  pinouts, schematics); VERA should offer "open in the default application" next to its own
  citation viewer instead of growing a tabbed multi-document viewer.
- OBSERVED: VERA can show a workbench file in its folder (`app.revealPath` →
  `revealPath` + `shell.showItemInFolder`, main reveal-path.ts) and open a recent workbench
  folder (`shell.openPath`), but cannot open a document with its default application.
- OBSERVED: on Windows `shell.openPath` runs scripts and executables (.js, .bat, .py with the
  launcher, .exe); citations and Docs paths can originate from model output.
Desired outcome: from the document viewer or a Docs row, the user opens that
  workbench document in the operating system's default application; files that are not
  documents on the allowlist are never opened.
Actors: the desktop user; the main process; the OS default application.
Primary scenario: the user opens a cited datasheet page in VERA's viewer, presses "Open in
  default app", and the PDF opens in their PDF reader.
Examples:
- docs/stm32g474.pdf → opens in the PDF reader; docs/pinout.xlsx → opens in Excel.
Counterexamples:
- tools/flash.bat, scripts/setup.py, docs/page.html → refused (not on the allowlist, RULING-001).
- ../outside.pdf, a link or a folder → refused like reveal.
In scope: one IPC channel opening a guarded workbench file with the default application, the
  shared allowlist, buttons in the viewer and Docs rows, errors, tests.
Out of scope: jumping to a page or cell in the external application; artifacts (they have
  their own reveal); managed downloads under .vera/downloads (OBSERVED: PathGuard permanently
  ignores .vera, so they would need a downloadId-based route; not requested); images and HTML (RULING-001); the side-panel viewer (TASK for proposal 2).
Constraints: on master; no commits unless asked; same path guard as reveal (PathGuard,
  ordinary file, re-checked identity before opening); no new error codes.
Success signals: a main-process test opens an allowlisted workbench document and refuses
  scripts, HTML, outside paths, links, folders and missing files without calling the opener;
  renderer test shows the buttons with accessible names and errors.
Evidence: main reveal-path.ts, index.ts handlers app.revealPath and workbench.recent; renderer
  documents/{viewer-context,docs-tab,downloads}.tsx; shared ipc.ts and errors.ts.
Assumptions: none; OBSERVED during specify that PathGuard refuses .vera, so downloads left scope.
Unknowns: none decision-blocking.
Decision-blocking questions: none open. Answered by the user (RULING-001): documents only.
Proposed behaviors (accepted by RULING-001 unless marked):
- Allowlist: .pdf .txt .md .markdown .csv .tsv .log .docx .xlsx .pptx .doc .xls .ppt .odt .ods
  .odp .rtf (case-insensitive); everything else is DENIED, including HTML, images and code.
- Not accepted, design detail: an OS failure to open (no associated application) is INTERNAL.

## Design

**Approach.**
- Shared `documents.ts` gains `externalDocumentExtensions` (RULING-001) and
  `opensExternally(path)`: the lower-cased extension of the last path segment is on the list.
  The renderer uses it to show the action only for allowlisted documents outside `.vera/`
  (REQ-UX-f5d6e9e4); main enforces it again (REQ-SEC-33b98d33), so the renderer is never the
  only gate.
- Main `reveal-path.ts` factors the existing guard of `revealPath` (PathGuard resolve, not the
  root, ordinary non-link file, identity re-check) into `guardedFile(root, path)`, reused by
  `revealPath` unchanged and by a new `openPath(root, path, open)`. `openPath` first refuses a
  path that does not open externally (DENIED), then guards, then awaits the opener; a non-empty
  error string from `shell.openPath` becomes INTERNAL (REQ-REL-85ae1f66).
  Rejected: opening by `file://` URL through `shell.openExternal` (protocol handlers, no
  Windows file association guarantees).
- Shared IPC gains `app.openPath {path} -> {}` beside `app.revealPath`; main wires it to
  `shell.openPath` through `sessions.run` like reveal (REQ-FUNC-d37a2092).
- Renderer: `OpenExternally({path})` (documents/open-externally.tsx) renders the button, its
  pending state and its error in place. The viewer header shows it for non-artifact content
  whose path opens externally and does not start with `.vera/`; each Docs row shows it for
  allowlisted paths (also for documents not indexed, such as legacy .doc).

**Interfaces and data.**
- `app.openPath`: request `{path: string(1..)}` relative to the workbench; response `{}`;
  errors DENIED (allowlist, guard, link, folder, root, .vera), NOT_FOUND (missing), INTERNAL
  (OS could not open). No state is stored.
- Locales en/ro/de: `documents.openExternal`, `documents.openExternalNamed` ({{path}}).

**Files and test seams.**
- shared documents.ts + documents-ipc.test.ts (allowlist); ipc.ts; main reveal-path.ts +
  reveal-path.test.ts (open allow/deny/INTERNAL with a fake opener); main index.ts;
  ipc-router.test.ts and bridge.test.ts channel lists; renderer open-externally.tsx,
  viewer-context.tsx, docs-tab.tsx, documents.test.ts; mocks mockApi.ts; locales.

**Risks and open decisions.**
- Security: the allowlist is the boundary for launching external programs; it is checked in
  main before any filesystem access. Legacy Office formats may hold macros; Office blocks
  them by default and the open is an explicit user action.
- The pre-existing failure of reveal-path.test.ts ("reveals an existing ordinary Unicode
  workbench file") writes .vera/.veraignore before creating .vera; it is outside this task
  and stays as is.
- No open product decisions.

**Requirement map.** REQ-FUNC-d37a2092: openPath + channel; REQ-SEC-33b98d33: allowlist in
main + guardedFile; REQ-REL-85ae1f66: opener error -> INTERNAL; REQ-UX-f5d6e9e4:
OpenExternally in viewer and Docs rows.
