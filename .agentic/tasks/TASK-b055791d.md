## Frame

Problem: VERA has no MQTT capability and no way to hand a plugin a private setting. OBSERVED: no plugin under
`05_Software/plugins/` speaks MQTT; the runner spawns programs with stdin closed and a minimal environment
(`runner.ts` programEnvironment, `node-process-host.ts` stdio ignore), and `00_Planning/plugins/architecture.md` §3.2
says credentials from the VERA store never enter a program's environment. The only private settings today are
provider keys and parts-search supplier keys, used by host code itself (OBSERVED `parts-access.ts`, `parts-env.ts`).

Desired outcome:
- An official plugin `mqtt-tools` (STATED ticket IOT-05) for subscribe, capture, payload validation and
  publish/request-response against a selected, configured broker (STATED); no broker administration and no publish to
  undeclared topics (STATED).
- An explicit broker connection profile: broker, TLS/CA/hostname verification, credential reference, client identity,
  protocol version, topic ACL, QoS and reconnect policy (STATED).
- A host integration that reads the secret from VERA's CredentialStore and hands it only to approved finite runs; no
  password in argv, manifest, `workbench.yaml`, prompt, log or artifact, and no change of the general environment
  inheritance of plugins (STATED ticket and plan §2). The capability exists only while the plugin is installed and
  enabled for the workbench; disabling it revokes host access (STATED T05-F). Configuration UI and the credential
  broker are this child's scope (STATED).
- Subscribe bounded by time, messages and bytes, wildcards bounded (STATED); payloads are untrusted data with a schema
  and size limit, never agent instructions (STATED).
- Publish may actuate: retain, QoS duplicates, session state and Last Will explicit; no retained commands, no automatic
  control Will; a physical command is never retried by default; a disconnect does not revoke a published message
  (STATED).
- Results `format: 1` under `arduino-iot-results/<run-id>/` keeping topic, raw payload, receive time and QoS/flags
  (STATED plan §3); new UI text in en/ro/de (STATED brief).

Actors: the user (writes the broker profile, stores the broker credential in Settings or the CLI environment, enables
the plugin, approves runs), the agent (runs `mqtt-tool`), VERA's program tools, approval gate and runner, the
CredentialStore (desktop main) or the CLI's memory store, the broker, and the device or fixture client on the broker.

Primary scenario: the user stores credential `bench` (username, password) in Settings > MQTT credentials, writes
`mqtt/bench.json` naming a TLS broker on the bench network, its CA file, `credential: bench`, client id prefix,
protocol 5, QoS 1, an ACL with a telemetry filter `vera-test/bench1/telemetry/#` and one command topic
`vera-test/bench1/cmd/led` with a response topic. The agent runs `mqtt-tool subscribe --profile mqtt/bench.json
--credential bench --topic vera-test/bench1/telemetry/# --duration 10`; VERA reads the credential at run start and
writes it to the helper's stdin; the helper verifies the broker's certificate and hostname, records each message (raw
payload, QoS, retain, dup, time) and ends at the first bound. A later `request` on the command topic, approved as
device-write, publishes once with a correlation id and waits for the matching response.

Examples: STATED T05-A...T05-F. T05-A: a certificate from another CA or a hostname mismatch is refused before any
MQTT packet; the secret appears in no log, argv or artifact. T05-B: a retained message delivered at subscribe time
and a QoS 1 redelivery are not reported as new events. T05-C: a retained command and a topic outside the ACL are
refused by default; a response with another correlation is not taken as the answer. T05-D: an absent broker, a
timeout, a revoked authentication and a reconnect each give an explicit state; a command is not sent again. T05-E:
Stop unsubscribes/disconnects where possible; an acknowledged publish or a delivered Will is never reported as
cancelled. T05-F: disabling the plugin removes the run before the credential is read. Example needing a value the
user has not given: the bench broker's host, port and CA (`<host>:<port>`), which the profile declares.

Counterexamples: STATED - no broker configuration, no public broker in tests, no publish to unknown topics, no
retained command, no automatic control Will, no default retry of a physical command, no credential in a plugin's
environment.

In scope: the package (manifest, README, skills, PEP 723 helper `mqtt-tool` with a support package and pinned
paho-mqtt), catalog/pack entries; the host credential hand-off (manifest declaration, program tools, runner/process
host stdin input, desktop and CLI composition); a desktop Settings section to store/remove MQTT credentials (IPC,
main service, renderer, en/ro/de); a local in-test broker with a TLS fixture CA and a fixture device; knowledge,
context, planning docs and the plan row.

Out of scope: broker administration (STATED); Mosquitto binaries or any external/public broker (STATED brief, needs
the user); IOT-07 Wokwi token and IOT-08 SSH identity (STATED plan §2); MQTT over WebSocket (INFERRED: not asked);
native Ubuntu proof on this machine (STATED brief: open blocker if not runnable).

Constraints: no commit/push (STATED brief); LF files; exact pins; formats stay 1 (memory, AGENTS.md); reuse the
previous children's pattern and LAB-01's registry only if a resource needs reserving (STATED brief); good enough over
perfect, 1-2 review rounds (STATED brief).

Success signals: T05-A...F software parts demonstrated by focused tests against a real local broker process over TLS
with authentication; core tests prove the secret travels only on stdin of an approved run of the enabled official
plugin; typecheck, lint and check:i18n green; plan row 5 built.

Evidence: OBSERVED `05_Software/src/libraries/core/src/plugins/{program-tools,runner,node-process-host}.ts`,
`ports.ts` CredentialStore, `apps/desktop/src/main/{credentials,parts-access}.ts`, `apps/cli/src/{parts-env,run}.ts`,
`shared/src/plugins.ts` programSchema, `plugins/bus-tools`, the IOT-03/04 hand-overs; `pip index` shows paho-mqtt

Assumptions: the bench network is reachable from the host running VERA (INFERRED from the scenario).

Unknowns: the user's real broker product, its ACL and TLS setup (UNKNOWN; the profile declares them); whether a real
device is available (UNKNOWN; none is connected per the brief, so device evidence stays open).

Decision-blocking questions: none. The brief and ticket fix the scope; secret channel, UI shape and test broker are

Proposed behaviors (not accepted until specify):
- Secret channel: the program declares `credentials {option, scope: mqtt}`; at run start, for the official enabled
  plugin only, the host reads `mqtt:<ref>` and writes one JSON line to the helper's stdin, then closes it.
- Sessions are always clean (no persisted session state); QoS 0/1 only; client id = profile prefix + random suffix.
- Subscribe reconnects per the profile's policy and records the gap; publish/request never reconnect after sending.
- `--retain` allowed only on non-command topics declared retainable; risk irreversible.

## Design

**Approach.** Two halves joined by one narrow seam. Host: a program may declare `credentials {option, scope: mqtt}`
(REQ-DATA-e6b1fa1a); `run_program` resolves the named reference at prepare (official tier, option once, entry exists:
REQ-SEC-dbbd21e5, REQ-FUNC-00c788bb), and at apply - after the plugin list is loaded again, so a disabled plugin is
undeclared before anything is read (REQ-SEC-9976af2e) - reads `mqtt:<ref>` through a new `ProgramHost.credentials`
port and gives the runner one JSON line as `input`, which the process host writes to stdin and closes
(REQ-SEC-3f57f781, REQ-FUNC-ba0396c0). Rejected: an environment variable (the plan forbids changing plugin
environments; `/proc/<pid>/environ` is readable by the user's other processes), a temp file (left behind on a crash),
and a host-side MQTT tool like parts_search (a new npm dependency and no reuse of the plugin model the ticket asks
for). Plugin: `mqtt-tool`, a PEP 723 helper on paho-mqtt 2.1.0 driving paho's synchronous `loop()` itself, so
paho never reconnects or resends on its own (REQ-REL-b1ff1dd3); the profile file decides everything the agent cannot.

**Interfaces and data.** Spec REQ-DATA-96d18686 fixes the manifest field, stdin line, IPC, CLI variables, profile,
operations, results and exit codes. `ProgramCredentials {has(scope, ref, signal), read(scope, ref, signal)}` in
program-tools; `RunRequest.input` and `ProcessSpawnOptions.input` (string, never persisted). Desktop main
`MqttCredentialService` over the existing `CredentialFile` (consent, `registerSecret`, checkpoint/restore as
parts-access does) plus `mqttProgramCredentials(credentials)` for the sessions' ProgramHost (REQ-SEC-1ffb429b); the
renderer panel `mqtt-credentials.tsx` in Settings section `mqtt` (REQ-UX-4b90fed2). CLI `mqtt-env.ts` builds a
memory map from `VERA_MQTT_PASSWORD_<REF>` (REQ-FUNC-f250eee7). Helper modules: `profile` (validation,
REQ-DATA-96d18686), `topics` (filter coverage, REQ-FUNC-3b81d7a2), `schema` (REQ-SEC-5307cbfe), `credential`
(stdin line, REQ-SEC-7eef441d), `connection` (TLS context with `check_hostname`, CONNACK mapping, REQ-SEC-bc6dcac7,
REQ-REL-023ba532, clean session and Will, REQ-FUNC-1bc7512d), `operations` (capture, publish, request),
`report`, `workspace` (byte-identical copy). State is per run; nothing persists between runs (clean sessions).

**Files and test seams.** shared `plugins.ts`, new `mqtt-credentials.ts`, `ipc.ts`, `index.ts`
(plugins.test.ts); core `ports.ts`, `node-process-host.ts`, `runner.ts`, `program-tools.ts`
(node-process-host.test.ts, runner.test.ts, new program-credentials.test.ts); desktop main `mqtt-credentials.ts`,
`index.ts`, `sessions.ts` (mqtt-credentials.test.ts), renderer `mqtt-credentials.tsx`, `settings.tsx`, `mockApi.ts`,
locales en/ro/de (mqtt-credentials.test.tsx); cli `mqtt-env.ts`, `run.ts` (mqtt-env.test.ts); package
`plugins/mqtt-tools/**`, catalog.yaml, packs.yaml; tests `tests/integration/mqtt-tools.test.ts` with
`tests/support/mqtt-test-broker.py` (stdlib asyncio broker: MQTT 3.1.1 and 5, TLS, users, ACL, retained store, fault
switches from a JSON control file, packet log), `tests/support/mqtt-fixture-device.py` (paho device that answers
commands, sends a decoy and telemetry) and `tests/support/make-mqtt-certs.py` (cryptography: CA, server, other CA,
wrong-host certificate) - REQ-TEST-a0450ac6; prepare-plugins test list.

**Risks and open decisions.** The broker log of the test broker may hold the password it checked; the oracle reads
only the helper's stdout, stderr, run log and run folder. Windows Stop is a tree kill, so the graceful unsubscribe of
REQ-REL-0ce1ae9a is provable only on Linux (open: native Ubuntu); on Windows the kept partial result is the
evidence. A running helper keeps the password it read until it exits; revocation acts at the next run start
(REQ-SEC-9976af2e). The default tests need paho-mqtt 2.1.0 on the toolchain Python (environment.md). A stored credential is not pinned to a broker host: it goes to whatever broker the approved, hash-bound profile names (open limitation; the README tells the user to read `broker.host` before approving). No real device
or product broker is proven.
