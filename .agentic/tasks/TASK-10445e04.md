## Frame

Problem: the plugin platform and the serial-monitor plugin let the agent list ports and capture consoles, but no plugin declares esptool, so the agent cannot identify an ESP32 chip or flash an image; the `esp32-identify` skill already tells the agent to run `esptool --port P chip-id` "when the esp32-esptool plugin is enabled" (OBSERVED: `05_Software/plugins/serial-monitor/skills/esp32-identify/SKILL.md` step 5), and plan step 1 "First ESP32 flash" ends with this package (STATED: plan.md step table "PLG-01…PLG-05, PLG-08, PLG-09"; ticket #65 goal "identify and flash ESP32 chips").
Desired outcome: an `esp32-esptool` plugin folder (plugin.yaml, README, skill `esp32-flash`) that the user installs from the folder; its program `esptool` installs through the bundled uv with `pip: "esptool>=5,<6"`, is probed with `esptool version`, and every esptool v5 command runs at the risk the specs name: `version`, `merge-bin`, `image-info`, `elf2image` safe; `chip-id`, `read-mac`, `flash-id`, `read-flash`, `verify-flash` device-read (they reset the chip into its bootloader); `write-flash`, `erase-flash`, `erase-region` device-write; the skill teaches the agent to take images and offsets from `build/flasher_args.json`, flash, verify, reset and capture the boot log with serial-monitor (STATED: ticket #65 scope; architecture §2.1 canonical example; packs §1.2, §1.4).
Actors: the engineer who installs both plugins, enables them and approves device commands; the agent, which runs `esptool` through run_program after loading `esp32-flash` (STATED: architecture §3.4 rule); serial-monitor, which this plugin requires (STATED: architecture §2.1 `requires: [serial-monitor]`).
Primary scenario: with an ESP32-S3 on COM7 and a built ESP-IDF project in the workbench, the agent lists ports (`serial list`), runs `esptool --port COM7 chip-id` (device-read card in `ask`), reads `build/flasher_args.json`, runs `esptool --chip esp32s3 --port COM7 write-flash --flash-mode dio --flash-size 2MB --flash-freq 80m 0x0 build/bootloader/bootloader.bin 0x8000 build/partition_table/partition-table.bin 0x10000 build/app.bin`; the device-write card lists the three files with their SHA-256; after approval esptool writes, verifies ("Hash of data verified.") and resets; the agent captures the boot log with `serial capture --port COM7 --reset` (STATED: ticket done-when 1-3; OBSERVED: architecture §4 "Approving `write-flash 0x10000 build/app.bin` therefore approves those exact bytes").
Examples: `esptool --port COM7 chip_id` (v4 spelling) is device-read like `chip-id` (STATED: brief "the matcher normalises `_` to `-`"; OBSERVED: esptool 5.6.0 accepts `chip_id` with a deprecation warning, `--help` run in the PLG-05 scratch runtime); `esptool version` prints `esptool v5.6.0` then `5.6.0` (OBSERVED: same esptool); an image rebuilt while its write-flash approval is pending makes the approved run fail with CONFLICT, so it needs a new approval (STATED: ticket done-when 3; OBSERVED: `program-request.ts:229` re-hashes approved files); an esptool 4.8.1 probe is outside the range (INFERRED from `version.range`).

## Design

**Approach.** Content only, like serial-monitor: `05_Software/plugins/esp32-esptool/` with `plugin.yaml`, `README.md` and
skill `esp32-flash` (RULING-001). No platform code changes: the pip install kind, resolver, rule matcher, gate, file
binding and runner carry it (Frame evidence). The agent runs program `esptool`; VERA runs
`<runtime>/tools/esp32-esptool/bin/esptool[.exe] <args>` (REQ-FUNC-b0d7c102). Rejected: a helper script that turns
`flasher_args.json` into arguments (one more program and approval surface; the agent reads the JSON with `read` and the
approval card shows the resulting files and hashes anyway, REQ-DATA-b4e317de); an `@flash_args` file (refused by the
platform before any rule).

**Interfaces and data.** Manifest: `format: 1`, `version: 1.0.0`, ecosystem `esp32`, `requires: [serial-monitor]`, program
`esptool` with `install: { pip: "esptool>=5,<6" }`, `version: { args: [version], match: 'v(\d+\.\d+\.\d+)', range:
">=5,<6" }` (REQ-FUNC-3b4c7274, REQ-REL-a69bbfc4), `timeout: 120`. Rules, in order (RULING-002):
`esptool {version,--help,-h}` and `esptool * {merge-bin,image-info,elf2image} *` safe (REQ-SEC-bfed58fa); one device-read
rule for the quick read commands and one with `timeout: 1800` for `read-flash`, `verify-flash`, `dump-mem`, both with
the note "Resets the chip into its bootloader." (REQ-SEC-c8cf4a75, REQ-FUNC-a3a042ec); `write-flash`, `erase-flash`,
`erase-region` device-write with `timeout: 1800` and the overwrite note, `load-ram` device-write with its own note
(REQ-SEC-b3fe3c10); `{write-mem,write-flash-status}` and `* --force *` irreversible with notes; the confirm word is the
matched command or `--force` (REQ-SEC-d1d8978f). Leading `*` admits global options (`--chip`, `--port`, `--baud`,
`--before`, `--after`); the matcher's `_`→`-` and lowercase cover v4 spellings. Unmatched lines keep device-write.
Skill `esp32-flash` (REQ-UX-6a22c4dc): command table with risks; procedure: `serial list` and the chip (`esp32-identify`),
always `--port` and `--chip`; read `build/flasher_args.json` (`flash_files` offsets relative to `build/`,
`write_flash_args`, `extra_esptool_args`) and pass explicit offset/file pairs; stop and ask when any entry is
`"encrypted": "true"` or `sdkconfig` enables `CONFIG_SECURE_BOOT` or `CONFIG_SECURE_FLASH_ENC_ENABLED` (first boot burns
eFuses); never `--force`, `--encrypt`, `write-mem`, `write-flash-status` unless the user asks; stop a background capture
on the port first (BUSY); require "Hash of data verified." per file, else `verify-flash`; boot log with
`serial capture --port P --reset --until ...`; a rebuilt image means a new approval.

**Files and test seams.** New `05_Software/tests/integration/esp32-esptool.test.ts` (integration project, compiled
`@vera/core`). Fixtures `05_Software/tests/fixtures/esp32-esptool/`: `esptool-5.6.0-help.txt` (recorded from esptool
5.6.0 `--help`), `fake_esptool.py` (stub with representative chip-id and write-flash output; records argv and the
SHA-256 of each existing file argument as JSON lines), `flasher_args.json` (an ESP-IDF esp32s3 hello_world layout). A fake
uv generated per test handles `tool install` (asserts the requirement, writes the stub as `UV_TOOL_BIN_DIR/esptool`:
on Windows an `.exe` launcher from pip's vendored distlib ScriptMaker, elsewhere a shebang script with mode 0755) and
serial-monitor's `sync --script` / `run --script` with PLG-08's fake pyserial. Seams: package + Provisioner
(REQ-FUNC-b0d7c102, REQ-FUNC-3b4c7274, REQ-REL-a69bbfc4 with stub versions 4.8.1, 5.0.0, 6.0.0); classifyCommand tables
(REQ-SEC-*, REQ-FUNC-a3a042ec); help parse (REQ-SEC-9c665082); replay SessionService with both plugins, the real
runner and approvals (REQ-TEST-fe972de0, REQ-DATA-b4e317de, REQ-SEC-f98d4fd3 by rewriting the app image while its
approval is pending); SkillCatalog + programPromptEntries + skill text (REQ-UX-6a22c4dc). REQ-PLAT-d2b3fa4a: manual.

**Risks and open decisions.** No board or network in tests: esptool's real output and reset behaviour are proven only by
the manual steps (REQ-PLAT-d2b3fa4a). Safe commands write host files (`merge-bin -o`, `elf2image -o`) without approval,
like other safe programs; a serial device named as their output file receives the bytes (accepted: architecture §3.2
does not sandbox programs, and the bytes are not a bootloader protocol). esptool without `--port` probes every port;
only the skill prevents it. The Windows stub launcher needs pip's distlib in the toolchain Python (python.org installs
ship pip).

**Requirement map.** REQ-FUNC-b0d7c102 manifest + provision test; REQ-FUNC-3b4c7274 version probe; REQ-REL-a69bbfc4
range; REQ-SEC-bfed58fa/c8cf4a75/b3fe3c10/d1d8978f rules; REQ-SEC-9c665082 rules vs recorded help;
REQ-FUNC-a3a042ec rule timeouts; REQ-UX-6a22c4dc skill; REQ-TEST-fe972de0 replay session; REQ-DATA-b4e317de and
REQ-SEC-f98d4fd3 no design impact (platform contracts, new linked tests); REQ-PLAT-d2b3fa4a manual.

**Manual board check (REQ-PLAT-d2b3fa4a), for the user.** On Windows 11, then on Ubuntu LTS, with an ESP32-S3 DevKit
on its USB (USB-Serial-JTAG) socket and an ESP32 DevKitC (CP210x) connected, and a prebuilt ESP-IDF `hello_world`
build for each chip (folder with `build/flasher_args.json`) copied into a workbench:
1. In `05_Software`: `npm run prepare:uv` once, then `npm run vera -- plugin install --path <abs>/05_Software/plugins/serial-monitor --data <dir>`
   and the same for `<abs>/05_Software/plugins/esp32-esptool`; the second shows `esptool` ready at 5.x (first install
   needs network for CPython 3.13 and esptool from PyPI).
2. Enable both (`plugins: { enabled: [serial-monitor, esp32-esptool] }`), start a session in `ask` and ask: "Identify the
   connected boards, then flash the S3 build to the ESP32-S3 and show me its boot log."
3. Expect `serial list` without a card, then `esptool --port <P> chip-id` with a device-read card naming the bootloader
   reset; the result names `ESP32-S3` (and `ESP32` for the CP210x board when asked).
4. Expect one `write-flash` device-write card whose files list bootloader, partition table and app with SHA-256 (compare
   one with `certutil -hashfile <file> SHA256` / `sha256sum`); offsets equal `flash_files` in `flasher_args.json`
   (bootloader 0x0 on S3, 0x1000 on the original ESP32). Approve; the output shows "Hash of data verified." per file.
5. Expect a `serial capture --port <P> --reset` card; the boot log shows the ROM banner and `main_task: Calling app_main()`.
6. Rebuild or touch-and-change the app image, ask to flash again: a new write-flash card with a different app hash; change
   the image again while that card is pending and approve: the run fails "changed after approval".
7. Repeat 2-5 for the ESP32 + CP210x board (bootloader offset 0x1000). On Ubuntu prefer the `/dev/serial/by-id/` path.
