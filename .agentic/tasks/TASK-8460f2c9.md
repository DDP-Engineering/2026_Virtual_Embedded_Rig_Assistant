## Frame

Problem: On Windows, VERA's opt-out does not reach ONNX Runtime. onnxruntime-node 1.30.0's `onnxruntime.dll` (win32 x64 and arm64) has no `ORT_DISABLE_TELEMETRY` string (OBSERVED string scan; the Linux and macOS libraries have it). The DLL registers the ETW TraceLogging provider `Microsoft.ML.ONNXRuntime` {3A26B1FF-7484-7484-7484-15261F42614D}, whose metadata carries provider group {4f50731a-89cf-4782-b3e0-dce8c90476ba}, Microsoft's telemetry group, which Windows' diagnostic data service collects (OBSERVED DLL metadata; `logman query providers -pid` on a Node and an Electron 44 process running an inference session). The process registers it even with `ORT_DISABLE_TELEMETRY=1`. So REQ-SEC-b4170ade is unmet on Windows, in the desktop (Whisper worker in the main process, embeddings in the Indexer utility process) and in the CLI (EmbeddingHost) (OBSERVED `main/index.ts`, `dictation/worker-host.ts`, `core/knowledge/document-services.ts`).
Desired outcome: On Windows, no VERA process that runs local inference registers ONNX Runtime's Microsoft telemetry provider, so its events are never written for Windows' diagnostic data service to collect. Local inference works as before (STATED user: task "Disable ONNX Runtime telemetry on Windows", "Do it here"; REQ-SEC-b4170ade).
Actors: desktop user on Windows (indexing, search, dictation); CLI user on Windows; release smoke.
Primary scenario: VERA starts on Windows -> the opt-out is set in the real main-process environment before any inference host exists -> the Indexer utility process and the Whisper worker load ONNX Runtime -> only ORT's own logging provider {929DD115-1ECB-4CB5-B060-EBD4983C421D} (no provider group) is registered, never {3A26B1FF-...}.
Examples: a Node/Electron 44 process with `ORT_RUNNING_UNIT_TESTS=1` set at runtime in `process.env` and ORT loaded in a worker thread: inference returns [2], `logman` lists {929DD115-...} but not {3A26B1FF-...}; without it, both are listed (OBSERVED probe 2026-11-22).
Counterexamples: `DisableTelemetryEvents` does not help: onnxruntime-node exposes no call that reaches it (INFERRED: no such name in its JS API or `dist`), and third-party measurements report that `ProcessInfo` is written before it can run and that the ETW enable callback turns events back on (UNKNOWN for us: ORT's GitHub repository returns 404, so its source can't be read).
In scope: the opt-out in the desktop main's first module and in core's EmbeddingHost constructor (Windows only for the new switch); a guard that the shipped ORT libraries still carry their switch names; a Windows release-smoke check that no Node utility process (where the Indexer embeds) registers the telemetry provider while real local inference runs, with the harness giving the app no `ORT_*` variable; REQ-SEC-b4170ade verification and paths; knowledge pages and smoke docs.
Out of scope: Python plugins' own runtimes (REQ-SEC-b4170ade covers VERA's local inference hosts); building ONNX Runtime with `--no_telemetry` (OBSERVED rawtonic PR #914 needed a full own build per platform); events already written by earlier builds (Windows' diagnostic data service owns them).
Constraints: the opt-out must be in the real process environment before ORT's DLL initializes; utility processes and worker threads inherit it (OBSERVED fork without `env` at `main/index.ts:231`). `inference-telemetry.ts` stays the main process's first import; it runs core's rule after @vera/core's modules, none of which starts a worker (RULING-004). Pre-release: no compatibility code (memory rule).
Success signals: focused unit tests (both platforms' branches); the guard test over the shipped libraries; the release smoke on this branch's rebuilt ZIP reports ORT's logging provider in at least one of the app's Node utility processes (where the Indexer embeds) and its telemetry provider in none, without elevation.
Evidence: string and metadata scans of `node_modules/onnxruntime-node/bin/napi-v6/*`; `logman` probes under Node 24.21.0 and Electron 44.11.4; IncarnaMind PR #2149 and rawtonic PR #914 (independent reports of the same Windows switch, untested on hardware there).
Assumptions: `ORT_RUNNING_UNIT_TESTS` changes nothing else in ORT 1.30 (INFERRED from both PRs' source reading; can't be checked here: source unavailable).
Unknowns: whether a future ORT release keeps reading `ORT_RUNNING_UNIT_TESTS` (the guard test and the smoke check catch a loss).
Decision-blocking questions: none. Relying on an internal ORT test signal is recorded as a ruling.
Proposed behaviors: (accepted, autopilot ruling) on Windows set `ORT_RUNNING_UNIT_TESTS=1` next to `ORT_DISABLE_TELEMETRY=1`, overriding inherited values; the smoke's Windows check above.

## Design

**Approach.** One rule, core's `disableOnnxRuntimeTelemetry(env = process.env, platform = process.platform)`: it sets `ORT_DISABLE_TELEMETRY=1` and, on `win32` only, `ORT_RUNNING_UNIT_TESTS=1`, overriding inherited values (RULING-001, RULING-002, REQ-SEC-b4170ade). The desktop main's first module imports it from `@vera/core` and runs it, so the Indexer utility process (forked without `env`) and the Whisper worker thread inherit it; evaluating core first is safe because none of its modules starts a worker on import (RULING-004). Core's EmbeddingHost constructor runs it before it creates a worker, which covers the CLI. On Windows the switch also reaches user terminals and agent shell commands through the inherited environment, as `ORT_DISABLE_TELEMETRY` already did (RULING-003). Rejected: `DisableTelemetryEvents` (no onnxruntime-node call reaches it; reported too late), an own `--no_telemetry` ORT build (a release change per platform).

**Interfaces and data.** Smoke (`smoke-windows.mjs`): `onnxRuntimeProviders` = `{ telemetry: "{3A26B1FF-7484-7484-7484-15261F42614D}", logging: "{929DD115-1ECB-4CB5-B060-EBD4983C421D}" }`; `etwProviderGuids(listing)`; `etwProviders(pid, run)` runs `logman query providers -pid <pid>` asynchronously with a 30 s timeout (no elevation), retries twice on 0x80071068 (a provider went away while logman read the list) and otherwise throws with logman's output. `nodeProcesses(metrics)` keeps the `node.mojom.NodeService` utilities, where the smoke's inference runs (the Indexer): renderers and the GPU process cannot load onnxruntime-node, and main runs it only for dictation, which the smoke does not use; one logman query of main took about 31 s and raced with its providers (smoke run 4). `inferenceTelemetryWatch({ query, alive })` gives `sample(metrics)`, `seenOnnxRuntime()` (one process listed ORT's logging provider in at least two samples, so a provider registered a little later is not missed) and `result()` = `{ status, processes: [{ pid, type, name, samples, onnxRuntimeSamples, onnxRuntime, telemetry, error?, exited? }], errors }`: FAIL when any sample saw the telemetry provider, when no sample saw ORT's logging provider (ORT not loaded: the absence proves nothing), or when a live process did not answer; flags once set stay set, and a process that exited before its query is recorded as `exited`. `sampleInBackground(sampleOnce, 250)` loops until `stop()`, which rethrows the error that ended it; `failed()` tells the wait it ended. The offline run starts sampling `getAppMetrics()` when the workbench is open, before `docs.reindex`, because ORT runs only while indexing embeds (`docs.search` is keyword-only); after the search it waits up to 60 s for `seenOnnxRuntime()` (or a failed sampler), stops, stores `offline.inferenceTelemetry` and asserts PASS. On an earlier failure the run's cleanup stops the sampler and stores what it saw. `isolatedEnvironment` strips `ORT_*`, so only the app can supply the opt-out. The runtime identity check `ortTelemetryDisabled` also requires `ORT_RUNNING_UNIT_TESTS=1` on Windows.

**Files and test seams.** `src/libraries/core/src/knowledge/embedding.ts` + `embedding.test.ts` (both platform branches, override of an inherited `0`, worker sees both at startup); `src/apps/desktop/src/main/inference-telemetry.ts` + `.test.ts` (import-time effect, first import, guard that the shipped onnxruntime-node libraries still carry their switch name: `ORT_RUNNING_UNIT_TESTS` in each `win32/*/onnxruntime.dll`, `ORT_DISABLE_TELEMETRY` in each Linux and macOS library); `tests/packaging/smoke/smoke-windows.mjs`, `smoke-package.mjs`, `smoke-runtime.mjs`; unit tests in `tests/packaging/windows-egress.test.ts` (recorded `logman` listing as fixture) and `package-smoke.test.ts` (`isolatedEnvironment`). Docs: `06_SoftwareDocu/release-package-smoke.md`.

**Risks and open decisions.** `ORT_RUNNING_UNIT_TESTS` is an internal ORT test signal: assumed to change nothing else in 1.30 (source unavailable). An upgrade that drops it fails the guard test and the Windows smoke. Sampling every 250 ms must catch ORT while it is loaded; the positive control turns a missed window into FAIL, never a false PASS. The Whisper and CLI paths set the variable at runtime in the same process; their proof is the Frame's Node and Electron probes, not the smoke; main's environment is checked by the smoke's identity check (`ortTelemetryDisabled`).

**Requirement map.** REQ-SEC-b4170ade: the rule, its two call sites, guard test, Windows smoke watch; verification and paths updated. REQ-SEC-f0170107 (command environments): no design impact (RULING-003).
