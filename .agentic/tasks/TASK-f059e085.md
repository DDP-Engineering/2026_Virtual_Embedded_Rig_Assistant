## Frame

Problem: VERA can test firmware only on a real board (LAB-03 HIL, LAB-04 GDB). It cannot run a firmware ELF on a
virtual board, so firmware behavior cannot be checked before the hardware exists or when no bench is available. OBSERVED: no
plugin under `05_Software/plugins/` drives a microcontroller simulator, and no manifest declares a Renode program.

Desired outcome (STATED, ticket LAB-06 #107 "Livrabile și operații" and coordinator brief):
- Plugin `renode`: a pinned Renode engine obtained through VERA's verified provisioning (SHA-256), with the platform model
  and the fixtures identified. The first target is one Cortex-M profile from the chosen version's documented support.
- Finite operations list-supported-profiles, validate-firmware, run, test, capture-UART and report. Loading a binary needs
  an explicit architecture, memory and boot address. A CPU in the simulator does not prove every board peripheral.
- Approved `.repl`/`.resc` profiles and test sets with identified local dependencies. VERA never runs an arbitrary
  model-generated monitor script, host Python/C# or hidden download commands, and it refuses disallowed includes.
- Initial tests for boot/version, UART, timer and one modeled peripheral. Sensor or communication stimuli are declared and
  reproducible, and unimplemented peripherals lead to unsupported/incomplete.
- Headless operation, with integration into Renode's official test mechanism (Robot) where it is available. Project custom
  keywords that execute on the host need separate approval or stay excluded.
- No default binding to a physical USB/UART, the external network or arbitrary host files.
- Virtual time and real time are kept separate, and timeouts have both a real and a virtual budget. A stuck test can be
  stopped with no process left.
- The report states exactly what was simulated (firmware, model, hash) and what is not covered: real electrical timing,
  analog consumption, EMI and SPICE circuit behavior.
- Done criteria L06-A...L06-H (STATED, ticket).

Actors: the user (owns the firmware and the workbench, approves runs, may add their own profiles and test sets in the
workbench), the agent (chooses the profile and test set, asks for runs, reads the reports), VERA core (rules, approvals,
runner, Stop, provisioning), the helper `renode-sim` and the Renode engine process.

Primary scenario (INFERRED from the ticket): the user has `build/app.elf` for an STM32F4 Discovery. The agent first runs
`renode-sim validate --profile stm32f4-discovery --firmware build/app.elf --arch cortex-m4 --boot-address 0x08000000`.
This check is offline: it reads the ELF machine and attributes, checks that the segments lie inside the profile's memory
and that the vector table sits at the boot address. The agent then runs `renode-sim test --profile stm32f4-discovery
--firmware build/app.elf --arch cortex-m4 --boot-address 0x08000000 --test-set board-basics --real-timeout 120`. The
helper copies the ELF into a new run folder and starts the pinned Renode headless, with a monitor script it composes
from the approved profile. It advances virtual time in slices, reads USART2 through a file backend in the run folder,
presses the modeled user button and reads the modeled LED. It writes `embedded-lab-results/<run-id>/` with result.json,
junit.xml, the UART log, the engine log and the report.

Examples:
- An RV32 ELF, or an ELF linked for an STM32G0 memory map, is refused by validate-firmware and never reported as a
  validated platform.
- A firmware that writes an unmodeled peripheral address yields `incomplete`, and the result names the address.
- A firmware that prints a wrong version is `fail` (an assertion). One that never prints is `timeout`, with the virtual
  budget it used.
- Stop during a test leaves no Renode process and a partial report that carries the run id.

Counterexample: the stock Renode script `scripts/single-node/stm32f4_discovery.resc` downloads its ELF from
dl.antmicro.com and runs `python`, so VERA refuses it and does not run it.

Proposed behaviors (accepted by ruling under the autonomous brief):
- P1 Two programs. `renode` is the engine: found or installed from a pinned download, and every direct call is blocked.
  `renode-sim` is the standard-library helper, with `profiles`, `validate`, `run`, `capture-uart`, `test`, `report` and
  `tools`.
- P2 VERA does not start Renode's Robot keyword server: it listens on every interface on Linux, and its `Execute
  Command` keyword reaches the monitor's `python`. The approved test sets are data (fixed step kinds), and the helper
  runs them over the monitor console. Results use the LAB-03 JSON/JUnit shape, and Robot Framework is not a dependency.
- P3 Profiles are data plus `.repl`/`.resc` files, validated line by line. `using` may name only the pinned engine's own
  `platforms/` files (with recorded hashes) or files beside the profile. Refused: URLs, `python`, includes from
  elsewhere, and host-binding commands (sockets, PTY, TAP/switch, GDB server, USB/IP, host files outside the run folder).
- P4 Every run copies the ELF into the run folder and records its SHA-256, its build id, the profile and the engine
  hashes. It writes result.json progressively, so a killed run leaves an identified partial report in state `running`,
  which `report` then marks interrupted. Each run enforces its own real-time budget below the runner timeout, and a
  virtual budget per run and per step.
- P5 Unmodeled peripheral accesses reported in the engine log make the result `incomplete`, naming the addresses. A
  firmware/profile mismatch is refused before the engine starts.
- P6 `report --run DIR [--hil DIR]` renders md/html/junit. It lines up the requirement ids of the virtual cases with the
  HIL steps that the test set names, in separate columns (virtual vs hardware).

## Design

Diagrams: [diagram_TASK-f059e085.md](diagram_TASK-f059e085.md)

**Approach.** The work is a plugin package only, with no core/shared/host change; the only platform-side edits are the
catalog and pack entries. Program `renode` is the engine: `find`, plus a pinned `download` per platform; every direct
rule is blocked (REQ-SEC-192d9739, REQ-FUNC-70f62b22). Program `renode-sim` (`uses: [renode]`) is a standard-library
helper and the only way in.

Every engine operation is one finite session with this primary flow:
1. Read and validate the profile, its `.repl`/`.resc` files and its engine files, the test set and the ELF. Refuse
   before anything starts (REQ-SEC-1190bf53, REQ-FUNC-ebfa3d95, REQ-REL-0423211e).
2. Create the run folder, copy the inputs into it and write result.json with state `running`.
3. Start Renode headless with piped stdio and send monitor commands composed only from the approved profile and fixed
   templates (REQ-SEC-01fae096).
4. Advance virtual time in fixed slices. After each slice, read the UART file backend and the engine log, then
   evaluate the steps (REQ-FUNC-4bf35c2a, REQ-FUNC-cea31393, REQ-FUNC-d89b80fd, REQ-REL-b66cb484).
5. Quit or kill the engine, and write the final result and junit.xml.

Leases are not needed, because there is no physical resource. That has a consequence: VERA's Stop and the runner
timeout are immediate tree kills (OBSERVED in `runner.ts`). The helper therefore keeps result.json current: it rewrites
it when the engine starts, when each case starts and ends, and after a slice once 2 s have passed (`heartbeat`). It
also enforces its own real budget below the runner timeout, which gives a clean `real-timeout` with the engine killed
(REQ-REL-c7579edf, REQ-REL-884979c1). `report` completes an interrupted folder (heartbeat older than 90 s) as
`stopped`/`interrupted`.

Rejected alternatives:
- Renode's Robot keyword server (ruling RULING-001 P2): it listens on every interface on Linux, and `Execute Command`
  reaches the monitor's `python`.
- Including the profile `.resc` verbatim: its lines are parsed and re-emitted instead.
- A runner change to give unleased runs a stop grace: not needed once the progressive result exists.

**Revised in build (real engine, review round 1).** The real Renode 1.17.0 changed four things:
- The vendor CPU file downloads an SVD in an init block. The profile therefore ships its own copies of the board and
  CPU files, and the engine files a profile uses are checked for init blocks and URLs (REQ-SEC-1190bf53,
  REQ-PLAT-d03a51af).
- Log lines interleave with the console unless `--hide-log` is passed. Setup commands answer nothing, so any answer
  is an error.
- Write paths resolve against the engine folder and quoted paths are refused. All `@` paths are therefore absolute,
  using the 8.3 short form or else `run-path` blocked.
- The UART file backend is exclusive on Windows, so segments are read after CloseFileBackend.

The start check (initial PC/SP equals the vector table) and the virtual-time cross-check are implemented in
`operations.py`.

**Interfaces and data.** The CLI, the profile/test-set/result formats, the statuses and exit codes are in spec
`REQ-DATA-8a943977.md`. Profiles and test sets live in the plugin (`profiles/`, `testsets/`) or in the workbench
(`renode/profiles/`, `renode/tests/`) and are validated identically. The step kinds (uart, count, stimulus, observe,
run) are fixed. Stimuli and observables must be declared by the profile; parameters are regex-checked and regex-escaped
(REQ-FUNC-d89b80fd).

Time is kept in two separate fields:
- Virtual time is the number of slices advanced times the slice length, cross-checked against the engine's
  `GetTimeSourceInfo`.
- Real time comes from `time.monotonic`.

Both budgets are recorded. The coverage block always lists what is not covered (REQ-FUNC-9431b520, REQ-FUNC-ea40de9f).
Determinism comes from the model plus fixed slices: line times are quantized to the end of their slice, and the
stimuli run at fixed virtual points (REQ-REL-a663fd2d). The report renders the hil-testing shape and, with `--hil`, a
requirement table in two columns (REQ-FUNC-31a21cb5).

**Risks and open decisions.**
- The engine's console framing, options and log formats were UNKNOWN at design time. They are now OBSERVED on the real
  1.17.0 and recorded in section 9 of the spec. Linux stays unobserved: the archive path is inferred, and the
  exclusive-open and diagnostics behavior is assumed to match.
- Workbench `.repl` validation is an allowlist for `using` combined with a denylist of constructs. A new Renode model
  type that binds a host resource and matches none of the denied words would pass. That residual risk is recorded in
  the skill and README, and the pinned engine version limits it.
- Renode writes its own temporary files under the system temp folder.
