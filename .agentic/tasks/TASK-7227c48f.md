## Design

**Approach.** Register the three fixed HTTPS routes in the shared hosted registry
(REQ-FUNC-5e200114). The existing Settings editor supplies search, explicit model entry,
connection testing and stable display of the selected service in model pickers.

**Interfaces and data.** Route these catalog projections through hosted-catalog.ts
(REQ-FUNC-5711221e, REQ-FUNC-3c53af08). Apply the service-native schemas from the spec.
Match sparse NVIDIA rows against pinned pi-ai NVIDIA chat metadata. Shared preset storage
and credential scope remain format 1. Avoid seeding the router catalogs with model suggestions
that could become unavailable. A saved ID remains an explicit choice when discovery fails
(REQ-REL-5d190476, REQ-REL-fffacb83).

**Files and test seams.** hosted-provider-presets.ts defines bindings, gateway-catalogs.ts
projects the three catalog formats, and curated-adapters.ts supplies documented Completions
options. The Desktop ProviderGateway connection test reserves enough output for reasoning
models on these services. Script the real settings and gateway with fixtures for scoped keys,
full IDs, negative catalog/model outcomes and a complete tool continuation
(REQ-FUNC-a05ea7ac). Exercise preset selection and manual entry in focused Chromium.

**Risks and open decisions.** RULING-001 replaces account-dependent smoke with
scripted proof. Missing capability data stays unknown. Account gating cannot be inferred
from a public model listing. Gateway routing takes place within the selected service.

**Requirement map.** See Requirement coverage and the protocol spec for the catalog.
Shared format, credential, cancellation, manual entry and connection-test requirements
use their existing implementation.
