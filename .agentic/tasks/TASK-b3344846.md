## Frame

Problem: VERA can build Zephyr projects (LAB-07) and flash/test/simulate firmware built elsewhere (LAB-03/04/06), but it
cannot inspect, build or test a PlatformIO project. OBSERVED: no plugin under `05_Software/plugins/` declares PlatformIO
(`ls plugins/`, 2026-11-14); no `pio`/`platformio` on PATH and no `~/.platformio` use is planned. The epic's integrated
acceptance (8 steps, L08-H) has no aggregate report yet (OBSERVED: plan page states "LAB-08 planned").

Desired outcome (STATED, ticket LAB-08 #109 "Livrabile și operații", criteria L08-A..H, "Acceptanță integrată", and the
coordinator brief):
- Plugin `platformio` with a pinned PlatformIO Core and the platforms/frameworks/toolchains of the fixtures installed
  explicitly and identified; not every board/framework of the catalog is promised.
- Operations inspect-project, inspect-environments, prepare-packages, build, size/artifacts, test-host, test-device,
  upload and clean, with an explicit environment and port/probe. The serial monitor stays the existing plugin's.
- `platformio.ini` and the effective configuration are parsed, including extends/extra_configs and the selected
  environment; paths with spaces/Unicode and several environments without a dangerous default choice.
- extra_scripts, custom upload commands, platform packages, hooks and targets such as upload/uploadfs/erase are in
  preflight and risk; not every `pio run`/`pio test` is safe; the test code of an unknown project is never run
  automatically.
- Package install/update/network are distinct operations; after explicit provisioning the fixture builds offline; no
  Remote Development, cloud login or project upload.
- The build keeps ELF/BIN/HEX, the environment, dependency versions, relevant settings and logs with hashes.
  Upload/test-device use the resource and approval infrastructure and never guess the port.
- Clean touches only the owned build/cache of the selected project and environment; never platformio.ini, the code or
  the user's global configuration.
- Integrated acceptance (8 steps) with LAB-01..07 evidence reused where still valid; a missing instrument/board is a
  blocked proof, never a ticked criterion (STATED, ticket and brief).

Actors: the user (owns the workbench, the project and the PlatformIO core folder, approves runs and the network step),
the agent (writes the request, chooses operations), VERA core (rules, approvals, runner, leases, BUSY, Stop), the
plugin's helpers, PlatformIO Core and the processes it starts (SCons, the compiler, the test program, the uploader).

Primary scenario (INFERRED from the ticket and brief): the workbench holds `platformio/disco.json` naming the project
folder, the environment `disco`, the core folder and an owned build folder. The agent runs `platformio inspect-project`
(files parsed, environments, findings), `platformio prepare-packages` once (network), then `platformio build`; the
result folder holds firmware.elf/bin/hex with SHA-256, the effective options of `disco`, the platform/package/library
versions and the build log. The ELF then runs on the LAB-06 Renode profile and can be a HIL plan's firmware.
`platformio test-host` runs the Unity suite of the `native` environment; `platformio test-device` builds the device
test firmware only; its verdict comes from a renode-sim or HIL run of that ELF.

Examples:
- A request without `environment` for build is refused although the project has `default_envs` (no default choice).
- `extra_scripts = pre:gen.py` in an `[env]` section reached through `extends` is listed in preflight with the file and
  its SHA-256 and refused until the request approves that hash.
- `targets = upload` in the selected environment, or `upload_protocol = custom`/`upload_command`, is a finding;
  a build never runs the upload target.
- A Unity suite with one `TEST_IGNORE` reports `skipped` for that case and the run `incomplete`, never `pass`.
- clean of a request whose build folder lacks VERA's marker is refused; the project's `.pio` folder is never touched.

Counterexample: `pio run -e disco` with the project's own `targets` default - never; the helper always names targets.

In scope: plugin `platformio` (manifest, PEP 723 helpers, support package, skill, README), fixtures (one project with
two STM32F4DISCOVERY environments and one `native` environment, Unity tests, extra_configs), stand-ins where the real
tool is not available, opt-in real-tool tests, catalog/pack entries, `prepare-plugins.test.ts`, the plan page, the
aggregate acceptance report and knowledge pages.

## Design

Diagrams: [diagram_TASK-b3344846.md](diagram_TASK-b3344846.md)

**Approach.** A plugin package only; no core/shared/host change: the LAB-01 runner, leases and serial/probe BUSY, the
LAB-04 `probe` kind, LAB-03 HIL and LAB-06 renode-sim are reused unchanged. Outside the plugin only
`plugins/catalog.yaml`, `packs.yaml`, `prepare-plugins.test.ts` (and the workspace.py copy check) change. Two PEP 723
helpers share `pio_support/`:
- `platformio` (`pio_tool.py`): every operation but upload. PlatformIO Core 6.2.0 is a pinned dependency and runs as
  `sys.executable -m platformio`, so the tool and the parser are the same code (REQ-FUNC-684b0afc).
- `platformio-upload` (`pio_upload.py`, `resources {--probe, [probe]}`): upload and release, separate because the lease
  option belongs to one program (REQ-FUNC-26fb0ed6).
Primary flow: load the request (`request.py`) -> parse with PlatformIO's `ProjectConfig` under the scrubbed
environment (`config.py`; no parser differential, the LAB-07 lesson) -> preflight (`preflight.py`) -> package check
(`packages.py`) -> build folder claim (`builddir.py`) -> run folder with `running` result (`result.py`) -> PlatformIO
with explicit `-e` and `-t` (`ops.py`, `tests.py`) -> diagnostics, artifacts, provenance -> final result. Refusals
happen before the run folder exists (exit 2). Rejected: running `pio project config`/`pio run --list-targets` for
inspection (starts PlatformIO's CLI and maintenance hooks); executing the platform's `platform.py` to learn its
packages in a safe operation (platform code) - the package check reads `platform.json` only and the proxy guards the
rest (REQ-SEC-bb7ede2f); PlatformIO's own uploader/serial reader for device tests (a second programming/reading path
beside HIL - L08-G), so test-device builds only and test-run binds renode-sim/HIL runs by ELF hash (REQ-FUNC-a98ab34c).

**Interfaces and data.** Spec REQ-DATA-865c8fbd: request, operations, preflight codes, environment, folder layout,
result and exit codes. PlatformIO workspace/libdeps redirected by `PLATFORMIO_WORKSPACE_DIR`/`PLATFORMIO_LIBDEPS_DIR`
into the owned folder (REQ-REL-7dde63c1, REQ-SEC-4a902240); the project's `.pio` is never written. Targets always
explicit (REQ-SEC-82cb079b). Test reports from PlatformIO's `--json-output-path` (test-host) and Unity console lines
(test-run) (`unity.py`, REQ-FUNC-427ebd28). Progressive result.json as in LAB-06/07 (REQ-REL-5800dc9e).

**Files and test seams.**
- Plugin `05_Software/plugins/platformio/`: `plugin.yaml`, `README.md`, `skills/platformio-projects/SKILL.md`,
  `scripts/pio_tool.py`, `scripts/pio_upload.py`, `scripts/pio_support/{cli,request,config,preflight,packages,
  environment,builddir,ops,prepare,tests,unity,diagnostics,artifacts,upload,registry,lifecycle,result,errors,
  elf,workspace}.py` (as built: tools lives in ops.py).
- Fixtures `05_Software/tests/fixtures/platformio/`: `board-demo/` (platformio.ini with `disco`, `disco_fast` (extends)
  and `native`; `common.ini` via extra_configs; `src/main.c` = LAB-06 board-basics protocol; `lib/lines/` pure logic;
  `test/test_lines/` Unity suite with an IGNORE switch and a FAIL switch; `test/unity_config.{h,c}` USART2 output),
  `stand-ins/` (a fake `platformio` package used only when `VERA_PIO_TEST=1` + `VERA_PIO_TEST_PACKAGE`, recording
  argv/env/PIDs, writing firmware from a LAB-06 ELF and test reports; a fake core with platform.json/package.json/.piopm).
- Tests `05_Software/tests/integration/platformio.test.ts`: package/rules, request refusals, preflight per hook,
  builddir/clean, stand-in build/test/upload, Stop through VERA's real runner, BUSY; opt-in `VERA_PIO_REAL=<scratch>`
  (real core after prepare-packages), `VERA_PIO_REAL_GCC`, `VERA_RENODE_REAL`. Helper Python from `VERA_PIO_PYTHON`
  (a uv venv with the pins); without it the helper tests are skipped.

**Risks and open decisions.** Project code (SCons, the platform builder, approved scripts, test programs) runs on the
host: approval is not a sandbox (REQ-SEC-6ec31a0f). Platform code adds packages the offline check cannot see: guarded
by the proxy. Open until the real tools: tool-scons install by `pkg install`, `buildprog` behavior, Unity's library
script, Renode boot of a CMSIS build, OpenOCD `adapter serial` placement.
