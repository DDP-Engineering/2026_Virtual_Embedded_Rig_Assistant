## Frame

Problem: The Interactive Browser runtime and the local Whisper dictation models can only be installed from the internet (storage.googleapis.com, huggingface.co), so a bench computer on a restricted corporate network cannot use them (STATED: "in medii corporatiste accesul poate fi restrictionat"; OBSERVED: `browser/runtime.ts` download(), `dictation/transfer.ts` downloadModelFile(), no local source except the test-only `VERA_TEST_BROWSER_ARCHIVE`).
Desired outcome: A VERA delivery carries these two components so that installation is completely offline; only the AI provider connection may still need the network (STATED: "astfel incat procesul de instalare sa poata fi complet offline (evident conexiunea la provider-ul ai poate necesita conectare net").
Actors: The person preparing a delivery (release tooling in `02_Tools/delivery`); the bench user installing VERA and enabling the browser runtime or a dictation model in Settings.
Primary scenario: The delivery folder contains the component files with SHA256SUMS; the user copies them to the offline computer, opens Settings > Web access or Settings > Dictation and installs the component from the copied file; VERA verifies it against the hashes pinned in the app and installs it with no network request.
Examples: Windows bench without internet installs Chrome for Testing 156.0.8078.4 from `chrome-win64.zip` (207,073,013 B, SHA-256 220021ec…) and Whisper Small from its archive, then uses both. None other supplied.
Counterexamples: A changed or truncated archive is refused and nothing is published (INFERRED from the existing pinned-hash rule REQ-SEC-92a60a12 and the dictation integrity check). A Chrome archive of another version is refused (INFERRED: the pin is exact).
In scope: Delivery tooling that builds the component files with hashes and records them in `delivery.json` and `delivery:verify`; the app installing the browser runtime and Whisper models from local files with the same pinned hashes; offline-install help en/ro/de/fr; focused tests (STATED in the card brief "Done when").
Out of scope: Making provider connections offline (STATED); vendor programs and plugin dependency kits, which already have their own path (OBSERVED `help/en/offline-install.md`); changing the pinned versions (INFERRED: not asked).
Constraints: On master, the repository's default branch (the user's standing rule: "nu schimbi branch-ul"); another task's uncommitted Settings/Providers changes share this checkout, so do not commit or revert them; pinned hashes stay the only trust anchor (OBSERVED REQ-SEC-92a60a12); main opens file dialogs, the renderer never supplies a path (OBSERVED `plugins.installArchive` route in `main/index.ts`); Windows and Linux x64 only (OBSERVED `browserRelease()`).
Success signals: An offline install of both components works from the delivery files on Windows and on Ubuntu (WSL2); a changed file is refused; `npm run delivery:verify` covers the new files; the help describes the procedure.
Evidence: `05_Software/src/apps/desktop/src/main/browser/{release,runtime,integrity}.ts`; `.../dictation/{catalog,transfer,integrity,models}.ts`; `02_Tools/delivery/{build-plugin-deps-kit,delivery-common,verify-delivery}.mjs`; `05_Software/help/en/offline-install.md`; `00_Planning/System.md` L5/L6; `.agentic/knowledge/{browser-runtime,dictation,plugins-provisioning}.md` (all OBSERVED 2026-11-21).
Assumptions: The upstream Chrome for Testing ZIP can be shipped unchanged, so its pinned archive hash verifies it (INFERRED from `release.ts` archiveSha256). The Whisper files can be shipped as the exact pinned files (INFERRED from `catalog.ts`).
Unknowns: The exact redistribution notice Chrome for Testing needs (UNKNOWN); whether the Xenova repositories carry a LICENSE file to ship (OBSERVED: none in the pinned file list).
Decision-blocking questions:
1. Packaging: separate component files next to the installer, a "full offline" installer variant, or plugin-like modules on the Plugins page?
2. How the app finds them: an "Install from file…" button on Web access and Dictation, a configured kit folder like `plugins.kit`, or both?
3. Which Whisper models the delivery carries: both, or only Small?
4. Licence notices: which notice files ship with the components?
Proposed behaviors (not accepted):
- A `components/` folder in the delivery with the unchanged Chrome ZIP per platform, one ZIP per Whisper model, notices and SHA256SUMS.
- "Install from file…" on Settings > Web access next to Install, and on each Dictation model row next to Download; main opens the picker, verifies against the pins and installs offline through the same staging and publication as the download.

## Design

**Approach.** The delivery ships the exact pinned bytes, so the pins already compiled into Desktop stay the only trust anchor (REQ-SEC-92a60a12, RULING-001). Desktop gains one more source for the two existing install jobs instead of a parallel installer: `BrowserRuntime.provision({ file })` copies the picked ZIP into `.installing/chrome.zip` through the same length/SHA-256 transform the download uses, then runs the unchanged extract, tree verification and atomic rename (REQ-FUNC-75aa4017). `DictationModels.installArchive(id, file)` starts the same queued job as Download; the job extracts the ZIP with core `extractZip` into `.<id>.stage` and the unchanged fingerprint and hash check decides before the rename (REQ-FUNC-17812cd0). Main opens the native picker, so the renderer never supplies a path (OBSERVED constraint from `plugins.installArchive`). A delivery tool, `delivery:components`, fetches the pinned files once on a networked machine and writes the `components/` part (REQ-FUNC-102c1232). Rejected: a `components.kit` folder setting (RULING-002), a full offline installer and plugin packages (RULING-001).

**Interfaces and data.**
- Shared: channel `browser.runtime.installFile` `{}` -> `BrowserRuntimeView`; channel `dictation.installFile` `{ id }` -> `DictationSnapshot`; the `downloading` model state gains optional `fromFile: true`, so the renderer labels it "Installing from file…" with an indeterminate progress bar.
- Browser file job: phase `verifying` while copying, then `installing`, then `ready`; a size or hash mismatch is `integrity` (REQ-SEC-92a60a12); an unreadable file (ENOENT, EACCES, EISDIR) is the existing `storage` failure; cancel uses the existing controller. An already verified tree returns `ready` without reading the file.
- Dictation file job: space check as for Download; `extractZip` limits = pinned total bytes and file+folder count; any extraction or verification failure other than ENOSPC/EDQUOT is `integrity` (REQ-SEC-a255c261); busy rules (`BUSY` while a job runs or a removal is pending) are those of Download. No `fetch` call exists on either file path.
- Picker closed without a file: main returns the current view or snapshot and starts nothing (REQ-REL-5b7d34d9). Instrumented builds read `VERA_TEST_COMPONENT_FILE` instead of the dialog; an empty value means "closed".
- Delivery part `components/`: `chrome-win64.zip`, `chrome-linux64.zip` (upstream names, unchanged), `whisper-base.zip`, `whisper-small.zip` (stored entries at catalog paths, nothing else), `THIRD-PARTY-NOTICES.md`, `SHA256SUMS`; `delivery.json` part `components` with files, Chrome version and model revisions. Pins come from `browserRelease("win32"|"linux","x64")` and `dictationCatalog`, imported from the TS sources as `embedding-payload.mjs` does. Any fetch failure or pin mismatch throws naming the file; the part is built in staging and moved by `commitPart`, so a failed build leaves the old part (REQ-REL-2bd264e3). `delivery:verify` checks the exact file set, each Chrome ZIP against its platform pin and each model ZIP's member list and member hashes against the catalog (REQ-REL-596aeb8a).
- Notices: generated per component (name, version or revision, source URL, licence) plus the Apache License 2.0 text from `02_Tools/delivery/licenses/Apache-2.0.txt`; Chrome for Testing is listed under Google's terms with its in-archive `ABOUT` and `chrome://credits` (REQ-DATA-4365c89e).

**Files and test seams.** `main/browser/runtime.ts` (+ `runtime.test.ts`: file source, no transfer call, mismatch, unreadable); `main/dictation/models.ts`, new `main/dictation/archive.ts` (+ `models.test.ts`: install from ZIP, extra member, other model, changed byte, traversal, not a ZIP, busy); `main/index.ts` routes; shared `browser.ts`, `dictation.ts`, `ipc.ts` (+ `ipc-router.test.ts`, `bridge.test.ts` channel lists); renderer `browser-settings.tsx`, `dictation-settings.tsx`, locales en/ro/de/fr, `mocks/mockApi.ts` (+ `dictation-settings.test.ts`, e2e `browser-controls.spec.ts` for the button and the closed picker); `02_Tools/delivery/components.mjs` (library), `build-components.mjs` (CLI), `verify-delivery.mjs`, `licenses/Apache-2.0.txt`, `05_Software/package.json` (+ `tests/tooling/components.test.ts` with fixture pins and a stub fetch); help `offline-install.md` x4. Native proof: a gated integration test `tests/integration/offline-components.test.ts` (`VERA_COMPONENTS_DIR`) installs the real platform Chrome ZIP and both real model ZIPs with a throwing transfer, run on Windows and in WSL Ubuntu.

**Risks and open decisions.** Redistribution of Chrome for Testing binaries is governed by Google's terms; the notices state them, but whether a given delivery may carry them is the distributor's call (UNKNOWN, reported to the user). The tooling test cannot fetch the real 700 MB of files; the gated integration run covers the real pins. Model ZIPs are stored, not deflated, because ONNX weights barely compress and stored entries keep `zipFiles` unchanged.

**Requirement map.** REQ-FUNC-102c1232 -> `components.mjs` build + `build-components.mjs`; REQ-REL-2bd264e3 -> staging + `commitPart`, named errors; REQ-REL-596aeb8a -> `verifyComponents` in `verify-delivery.mjs`; REQ-DATA-4365c89e -> `formatNotices`; REQ-FUNC-75aa4017 -> `provision({ file })`; REQ-SEC-92a60a12 -> shared verified copy; REQ-UX-f17b5648 -> Web access button; REQ-FUNC-17812cd0 -> `installArchive` + `archive.ts`; REQ-SEC-a255c261 -> integrity mapping in `archive.ts`; REQ-UX-3c6ae462 -> Dictation row button; REQ-REL-5b7d34d9 -> main routes; REQ-UX-b1d7a8d6 -> help x4.
