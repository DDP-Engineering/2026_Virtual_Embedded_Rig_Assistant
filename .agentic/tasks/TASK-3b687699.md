## Frame

Problem: Behavior limits that users want to tune are code constants or hidden `settings.json` values. There is no place in the interface to change them per application, workbench or session (STATED: "o parte din aceste setari trebuiesc expuse in interfata sub o sectiune ADVANCED. Desired outcome: A framework for Advanced settings. One shared registry describes each setting: key, allowed range, default, the scopes it supports and when a change applies. Values are stored per application (`settings.json`), per workbench (`workbench.yaml`) and per session (durable session event). One resolver gives session > workbench > application > default. Advanced sections appear in Settings, Edit workbench and the session menu once "Show advanced settings" is on. The CLI accepts the same settings. The pilot setting "Tool calls per turn" runs through all of it (STATED: the user chose the pilot).
Actors: The user in the desktop app (Settings, Edit workbench, session menu); a CLI user; the session runtime that reads the resolved value.
Primary scenario: The user turns on Show advanced settings, sets Tool calls per turn to 100 for the application, to 200 for one workbench and to 300 for one session. A turn in that session can make 300 tool calls; a new session in the workbench gets 200; another workbench gets 100. Reset on the session value returns that session to 200. After a restart the session still has 300.

## Design

**Approach**: A single registry in `shared/src/advanced-settings.ts` describes every Advanced setting:
- key, value kind (int or boolean), min, max, default;
- the scopes it supports;
- when a change applies (live, new, reindex, reopen, restart).

Stores keep raw maps, and validation happens at two points. Saving goes through strict patch schemas built from the registry and rejects a bad value with INVALID (REQ-DATA-96ef3dd6). Resolving checks each stored value against the registry and skips an invalid one, reporting it through an `onIgnored(scope, key)` callback (REQ-DATA-33a90ef2). As a result, a hand-edited file never fails to load.

`resolveAdvanced(key, { session, workbench, app }, onIgnored?)` returns the most specific valid value, else the default. Each value is checked against the registry range, never against the other scopes, so a workbench or session value can raise or lower the app value (REQ-FUNC-902313e0).

Rejected alternative: strict zod objects in each stored schema. One out-of-range value would then make `settings.json` or `workbench.yaml` fail to load.

**Interfaces and data**:
- **App scope.**
  - `settings.json` replaces `limits` with `advanced?: Record<string, unknown>`, plus `showAdvanced?: boolean` (default false). This follows RULING-002: there is no migration, and `defaultSettings` writes neither key.
  - `settingsPatchSchema` gains `advanced: advancedPatchSchema("app")`, where each registered key is `value.nullable().optional()` and null removes it, plus `showAdvanced: z.boolean().optional()`.
  - `mergeSettings` merges `advanced` and drops nulls.
- **Workbench scope.**
  - `workbenchSchema` gains `advanced: z.record(z.string(), z.unknown()).optional()`, and `workbenchPatchSchema` gains `advanced: advancedPatchSchema("workbench")`.
  - The workbench service writes it into `workbench.yaml`; null removes the key.
- **Session scope.**
  - `session.updated` gains `advanced?: Record<string, number | boolean | null>`. The reducer merges it into a new optional state field `advanced` and drops nulls.
  - New IPC `session.advanced.set { sessionId, key, value | null }` calls `SessionService.setAdvanced`. That method validates the value against the registry for the session scope, and returns DENIED for read-only workbenches and archived sessions. It records the change in one transaction, so the value survives a restart (RULING-003).
- **Runtime.**
  - `SessionHost.maxToolCallsPerTurn` is replaced by `SessionHost.advanced?: { app(): Record<string, unknown>; workbench(): Record<string, unknown> }`.
  - `startTurn` resolves `toolCallsPerTurn` from the session snapshot, then workbench, then app, then 50. It logs ignored keys by key only (REQ-FUNC-2e124a88). The desktop main and the CLI supply the host.
- **CLI.** `--advanced key=value`, repeatable, last value wins. `args.ts` validates each value against the registry for the session scope; an unknown key or out-of-range value is a usage error with exit code 2. `run.ts` calls `setAdvanced` on the run's session before sending (REQ-FUNC-181db660).
- **UI.**
  - **Settings > Advanced**: a new nav section that always holds the Show advanced settings switch. When the switch is on, it also shows the app fields (REQ-UX-fcd1ad10).
  - **Edit workbench > Advanced**: a section added to `configSections` only when the switch is on.
  - **Session menu > Advanced…**: a menu item, shown only when the switch is on, that opens a dialog.
  - **Shared `AdvancedField`** (REQ-UX-9ea9184f):
    - a number input whose placeholder is the inherited value and its source;
    - a Reset button;
    - an apply-timing icon with a localized tooltip;
    - a localized range message shown on invalid input, which disables Save.
  - **Saving**: the app and session fields save at once, like the other Settings pages. The workbench fields save with the workbench Save at the top right.
- **Help.** `help/{en,ro,de,fr}/advanced-settings.md` covers the switch, precedence, timing icons and the pilot's range and default (REQ-UX-504e0d6d). It is linked from the help index.
