## Frame

Problem: VERA cannot simulate a circuit. STATED (ticket ELEC-04, #96): a plugin `ngspice` must run reproducible local
simulations on Windows and Linux - validate, run, measure, sweep, compare, report - with strict request files,
batch and non-interactive, in its own run folder. OBSERVED (2026-11-13): no ngspice console engine is installed here
(KiCad 10 ships only `ngspice.dll`); a script program cannot learn the path of another program of its plugin, so a
helper cannot reach a VERA-downloaded engine; VERA's provisioner unpacks `.zip` and `.tar.gz/.tgz/.tar.xz` only,
while every official ngspice Windows build is `.7z`.

Desired outcome:
- With the plugin enabled, VERA finds the user's ngspice or, on Windows, installs the pinned official ngspice-47 build
  (SHA-256 recorded, licence recorded) at the user's action; on Linux it finds the distribution's ngspice.
- The agent runs `ngspice-tool` operations on a netlist file and its local models: the helper validates the netlist
  and its include/lib chain before the engine starts, runs ngspice in batch mode in a new run folder, and writes the
  log, the effective netlist, model hashes, numeric series (CSV), a plot (SVG) and a criteria report.
- Measurements (min, max, RMS, average over declared windows, ripple after settling, overshoot, settling time, average
  power from v(t) x i(t) with a checked sign convention) and pass/fail criteria declared before the run; sweeps of a
  parameter or temperature and seeded Monte Carlo tolerances; a comparison of two runs that names what changed.
- Hostile netlists (shell or control commands, binary/OSDI/code-model loading, includes or outputs outside the
  allowed roots) are refused before the engine runs; inputs stay unchanged; Stop and timeout leave no engine running
  (ngspice writes its series only at the end, so they leave no partial series - RULING-003); non-convergence, a missing model or a pin mismatch never produce a pass.

Actors: the user (enables the plugin, installs ngspice or lets VERA install it, writes or exports netlists); the agent
(writes requests, runs ngspice-tool); VERA's provisioner and runner; the ngspice engine.

Primary scenario:
1. The user enables `ngspice`; on Windows without ngspice, Install programs downloads ngspice-47 (13.8 MB 7z).
2. The agent writes a request for `buck.cir` (transient 0..2 ms, measurements: output ripple after 1 ms, average
   power in the switch) and runs `ngspice-tool run --input request.json`.
3. The helper validates the netlist, copies it with its models into the run folder, runs `ngspice -b -n`, reads the
   series and reports the measurements against the declared criteria.

Examples (STATED, ticket Done criteria):
- E04-A: resistive divider, RC filter and rectifier match analytic or independent references within tolerances
  declared before the test.
- E04-B: a switch/transistor circuit shows v(t), i(t), average losses and the measurement window; a simple RC thermal
  model equals ELEC-01 at steady state (1 W into 50 K/W from 40 C gives 90 C).
- E04-C: missing model, mismatched pinout, non-convergence and insufficient data give no false pass.
- E04-D: sweep and Monte Carlo keep the seed and the inputs; a comparison shows the changed parameters.
- E04-E: external includes, executable directives and disallowed output paths are refused before the engine runs;
  inputs unchanged.
- E04-F: real batch runs on Windows and native Ubuntu show artefacts, errors, Stop and timeout.

Counterexamples: a non-converging run is not retried with relaxed solver tolerances; the peak of p(t) is never reported
as the average dissipation; adding a temperature node does not make a device model electrothermal.

In scope:
- STATED: plugin `ngspice` with a pinned, verified ngspice (find or controlled download, hash and licence recorded) and
  helper `ngspice-tool` (validate, run, measure, sweep, compare, report); analyses op, dc, ac, tran, plus noise where
  the models support it (marked not applicable otherwise); measurements and criteria; seeded sweeps and Monte Carlo;
  explicit lumped RC electrothermal networks; directive allowlist and include/lib chain checks; run profiles bounding
  duration and output; Windows and Ubuntu evidence.
- STATED (user, 2026-11-13, RULING-001): the user's ngspice when found, else the pinned official download.
- INFERRED (needed by RULING-001): two platform extensions - a Windows-only `.7z` download form extracted by
  System32 bsdtar with a bounded tolerance for its "unreadable filename" skips, and a program field `uses` that gives a
  script program the resolved path of a sibling program as `VERA_PROGRAM_<NAME>`.

Out of scope (STATED, ticket): firmware simulation, universal IC models, automatic correlation with the whole PCB,
replacing physical measurements; redistributing manufacturer models; OS memory limits the runner does not have.
INFERRED: generating a SPICE netlist from KiCad inside VERA (the user exports it; a KiCad-exported netlist is accepted
as input).

Constraints: same branch feature/93-electronics-calc; commit when validated, no push, no Claude attribution; do not

## Design

**Approach.** Three parts. (1) Two small platform extensions (RULING-002): `downloadForm` gains `7z` (Windows only),
extracted through the existing `tarCommand` with a bounded exit-1 tolerance; programs gain `uses`, resolved by the
provisioner, which adds `VERA_PROGRAM_<NAME>` to the script's `ResolvedProgram.env` (the existing hook for extra
variables - no change to the runner or program tools). (2) The plugin manifest: engine `ngspice` (find + pinned
download), helper `ngspice-tool` (`uses: [ngspice]`), rules blocking direct engine runs. (3) `ngspice-tool`, a
standard-library helper on the ELEC-01..03 conventions: it parses the netlist itself (netlist.py) and refuses before the
engine; it copies the chain into the run folder, rewrites includes, appends its own control block and runs
`ngspice -b -n` as a child with a deadline that kills it (engine.py); measurements are pure Python on the parsed series. Rejected:
loading KiCad's ngspice.dll through ctypes (ties to KiCad, not the approved download); a 7z library (new dependency).

**Interfaces and data.**
- shared `plugins.ts`: `downloadForm` -> "zip" | "tar" | "7z" | "file"; program schema `uses` (1..8 names) with the
  same-plugin, find/download-only, no-self, unique checks; `.7z` only under `windows-x64`.
- core `archive.ts`: `bsdtarSkipsOnly(output)` predicate; `provisioning.ts` extraction treats `7z` as tar and accepts
  exit 1 when the predicate holds; `resolve` adds sibling paths for `uses`.
- plugin: `plugin.yaml`, README (version 47, SHA-256, licence), skill `circuit-simulation`, catalog `official`, pack
  electronics group "Simulation (ngspice)".
- helper `scripts/ngspice_support/`: `cli.py` (argparse, operations, emit within 11 000 units), `request.py` (strict
  request reading, quantities, profiles), `netlist.py` (logical lines, cards, allowlist, includes, models, subckt
  pins), `engine.py` (find the engine from `VERA_PROGRAM_NGSPICE`, else PATH and the find locations; run folder copy,
  effective netlist, child process with deadline and tree kill, log classification, wrdata parsing), `measure.py`,
  `sweep.py`, `compare.py`, `report.py` (result.json, report.md, CSV, SVG, all-or-nothing writes), `workspace.py`
  (byte-identical copy).

**Files and test seams.** core `plugins/archive.test.ts` and `provisioning.test.ts` (7z tolerance with a stand-in
tar output, `uses` env), shared plugin-manifest tests (`uses`, 7z platform); `tests/integration/ngspice.test.ts` with
`tests/fixtures/ngspice/` (netlists, hostile netlists, requests, README with tolerances declared before the run):
offline refusals always; real-engine cases when the helper finds ngspice (here the extracted pinned build via
`VERA_TEST_NGSPICE`), opt-in `VERA_NGSPICE_UV` through the provisioner and runner (real 7z install, Stop).

**Risks and open decisions.** Executing netlists is the risk: the allowlist plus `-n` (no .spiceinit) plus a helper-only
control block keep commands out; spinit of the engine still loads its own code models (shipped with ngspice). Ubuntu's
ngspice version and log wording are unconfirmed until a host exists. bsdtar tolerance is bound to exact lines and the
pinned hash.
