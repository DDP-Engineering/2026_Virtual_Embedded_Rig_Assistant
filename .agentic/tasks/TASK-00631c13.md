## Frame

Problem: VERA has the electrical model, catalog, protection and motor-drives results and QElectroTech schematics, but
nothing that turns them into a control panel: no equipment list (BOM) with accessories, no terminal or 24 V supply
budget, no physical arrangement on rails, no dissipation or thermal check and no assembly verification record
(OBSERVED: core src/electrical has no panel code; electrical-schematics.md lists CAD-02 planned; motor_drives
`assemblies` are "for a later ECAD adapter", shared electrical-model.ts).
Desired outcome: plugin `panel-engineering` (ecosystem electrical, PolyForm NC, help en/ro/de/fr, pack "Electrical
schematics and panels") with product code in core and tools gated on its own plugin ID (STATED: brief). A panel file
(`electrical-automation-panels/<id>.json`, format 1) declares the board, enclosure and mounting plate (catalog items),
rails, ducts, zones with documented access/segregation rules, equipment (tag, catalog item, location, zone/rail, motor),
terminal strips, the 24 V supply, scenarios, declared reserve and thermal conditions (ambient, installation,
heat-transfer coefficient, ventilation). `panel_engineering_check` evaluates it against a CURRENT motor_drives result,
the model and optional .qet schematics and stores one new result: BOM with accessories and reconciliation, terminals,
24 V budget per scenario, 2D placement with collisions/zone/depth/missing-data findings, dissipation per scenario,
thermal evaluation within the stated method domain, short-circuit/busbars not evaluated unless data supplied, and an
assembly verification report listing characteristics, method, evidence and uncovered checks, never claiming IEC 61439
conformity (STATED: ticket CAD-02, brief). `panel_engineering` (read) drafts equipment from assemblies, shows which
parts of a stored result a changed device affects, and exports the BOM (CSV) and layout (SVG) of a stored result.
Actors: the agent with the plugin loaded; the engineer who writes/approves the panel file and the result (STATED: ticket).
Primary scenario: plant M (fixture) has current network, protection and motor_drives runs (M1 DOL, M2 star-delta); the
engineer has a 600x400x200 enclosure with plate, two rails and a terminal rail; the agent drafts equipment from the
assemblies, writes the panel file, runs the check with the M1/M2 .qet candidates; the result shows the BOM reconciled
with assemblies, schematic labels and the model, required motor terminals, the PLC on the 24 V supply with reserve, every
device placed or flagged, Ti per scenario against device limits; after the engineer swaps one contactor, the impact view
lists the BOM line, its rail, and the dissipation/thermal scenarios as affected (INFERRED: from CAD-02-A..D).
Examples: Schneider guide example NSYSF20840 against a wall, 800 W: S = 4.13 m², Ti - Te = 800/(5.5 x 4.13) ~ 35.2 K
(OBSERVED: Schneider enclosures catalogue p. 8/110 via storage.electrika.com page691); LRD21 is compatible with LC1D18
and mounts under the contactor (OBSERVED: se.com LRD21 page, Main "Product compatibility", "Mounting support").
Counterexamples: a fuse link placed without a holder because "it fits"; a missing dissipation read as 0 W; a result
stating "IEC 61439 compliant"; busbar or short-circuit withstand derived from the device list (STATED: ticket); a 3D
layout or machining file (STATED: ticket "no 3D").
In scope: shared panel file schema and result `panel` section; core pure engine (BOM, reconcile, terminals, budget,
placement, dissipation, thermal, verification report, impact, exports); tools; units heat-transfer and airflow;
catalog parameters width/height/depth/powerLoss/coilPowerLoss/powerConsumption/outputCurrent/airflow; cited fixture
data (se.com pages read 2026-11-16) added to cat-motor-drives and a new panel catalog; plugin package, skill, help, pack,
catalog; i18n tool texts; spec, requirements, knowledge, plan page, CHANGELOG, release notes.
Out of scope: 3D layout, machining files, IEC 61439 verification itself, busbar design, wiring/cable lists and document
exports beyond BOM CSV and layout SVG (CAD-03), heat from solar radiation, temperature stratification (STATED: ticket,
plan CAD-03 row).
Constraints: formats version 1, no migrations; reuse model, catalog, result-change/commitChange/write queue, PathGuard,
QET reader, gating; no new dependency; targeted tests; no commit; cited or self-authored fixtures (STATED: brief).
Success signals: CAD-02-A..D focused tests green with the cited fixture; thermal values equal an independent
calculation (hand reference from the Schneider method, tolerance preset 0.5 %); lint, typecheck, check:i18n, help and
release-notes checks green.
Evidence: ticket F:/ProjectsDDP/VERA_Electrical_Automation_Plugins_Tickets/CAD-02.md; plan file; electrical-schematics.md;
electrical-model.md; se.com product pages LC1D09P7, LC1D18P7, GV2ME10, LRD21, ABLS1A24050, TM221CE16T, NSYS3D6420,

## Design

**Approach**: a pure engine `analyzePanel` in core electrical/panel.ts (like motor-drives.ts) produces one
ElectricalResult with an optional strict `panel` section; panel-tool.ts reads the files (model, panel file, catalogs,
.qet via readQetFile, the CURRENT motor_drives result and the network run it chains to) and prepares the result
through `prepareResultChange` (REQ-FUNC-b0b55ff0). Read views draft/impact/export are pure functions over the stored
result plus current files (REQ-FUNC-40a5f935, -dd7ad54a, -7a0835ed). Rejected: equipment as model objects only (the
model has no geometry and the assemblies' per-motor tags collide); a multi-file result (the write flow is one file).
**Interfaces and data**: shared panel.ts `panelSchema` (kind vera-panel, format 1) + `panelDir`; result section
`panel` in electrical-model.ts (optional, checked by checkResult); units: heat-transfer `W/(m²·K)`, airflow `m³/h`,
known properties width/height/depth/powerLoss/coilPowerLoss/powerConsumption/outputCurrent/outputVoltage/airflow/
heatTransferCoefficient/internalTemperatureMax/wiringLoss/shortCircuitRating. Catalog value pick = confirmed,
conditions covered (catalog.ts `covers` exported), largest (REQ-FUNC-39b7793a). Errors: `Invalid panel file <id>:`
(REQ-DATA-a8bf1713); refusals before any change (REQ-REL-665727e6).
**Files and test seams**: shared panel.ts, electrical-model.ts, units.ts, catalog.ts (export covers), core panel.ts,
panel-tool.ts, report.ts (panel section), result-change.ts (tool name), tools.ts gating, registry, changes/events/
session-state tool names, desktop workbench-tools + locales; plugin package; fixtures tests/fixtures/panel-engineering
+ cat-motor-drives values; tests/support/panel_thermal_check.py. Unit tests panel.test.ts (engine), tool tests
panel-tool.test.ts (fixture chain network -> protection -> motor_drives -> qet candidates -> panel).
**Risks and open decisions**: adding known properties could invalidate existing models using those names with other
units (none found in fixtures); cat-motor-drives gains values, its version bumps to 2026-11-16.1.
**Requirement map**: DATA-a8bf1713 schema+semantic check; FUNC-a0fb1b98 BOM/reconcile; -cc5f6c3c accessories;
-a7c2c1de terminals; -4017a1ee budget; -0487d376 placement; -39b7793a dissipation; -c3a96daf thermal; -865665b6
sc/busbars; -f761244d verification list; -b0b55ff0 prepared result; REL-665727e6 refusals; -40a5f935 impact;
-dd7ad54a exports; -7a0835ed draft; TEST-265439fc fixtures/script; SEC-4dfa2a5b gating; UX-d32cc9db texts.
