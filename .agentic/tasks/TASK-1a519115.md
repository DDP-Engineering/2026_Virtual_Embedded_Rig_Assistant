## Frame

Problem: plugins install only from a folder or zip the user already has (OBSERVED `PluginStore.install` records tier `local`, `core/src/plugins/store.ts`; Plugins page offers only folder and zip pickers, `renderer/components/plugins.tsx`); nothing publishes plugins, lists them by pack, verifies a downloaded package or tells the user that a newer version exists (OBSERVED: no catalog code in `05_Software/src`), and official plugins exist only as source folders (OBSERVED `05_Software/plugins/`, PLG-08 RULING-001).

## Design

**Approach.** Three layers over the existing store. (1) Shared `plugin-catalog.ts` owns every format and pure rule: index, packs.yaml and catalog.yaml schemas, the token lint, semantic version order, the catalog URL rule and the IPC shapes (REQ-DATA-b40d3f9b, REQ-SEC-5fa5cd5e, REQ-SEC-a3c31442); `program-rules.ts` gains `ruleNamesProgram(match, program)` so the "program without rules" check uses the matcher's own normalisation (REQ-SEC-dfc6a26d). (2) Core `catalog-source.ts` checks and builds a catalog source with the store's own package reader, so CI and install see one definition of a valid package (REQ-FUNC-3b9f62f8, REQ-FUNC-f4381792); the CLI's `vera catalog check|build` is the CI and release step. Core `catalog.ts` is the client: `PluginCatalog.view/review/install` over an injected `fetch`, reading either the remote folder or the bundled folder through one verified read path (REQ-FUNC-98ded47a, REQ-SEC-449e334b, REQ-SEC-6305d7b7, REQ-SEC-69f9d44d, REQ-FUNC-f244f8f6, REQ-FUNC-46079512). (3) Desktop main composes it with `net.fetch`, adds three IPC channels and a 24 h `CatalogChecks` timer (REQ-FUNC-ce542246); the Plugins page gains a catalog section in a new `plugin-catalog.tsx` and reuses the existing Review screen for catalog installs and updates (REQ-UX-72a349a1, REQ-UX-c55a0fe1, REQ-UX-9207423e). The official plugins folder becomes a catalog source (packs.yaml, catalog.yaml, CONTRIBUTING.md, `.ci/` workflow template); `prepare:plugins` builds it into `src/bundled-plugins/` and packaging ships that as `<resources>/plugins/` (REQ-PLAT-720aa4f2). Rejected: index signing (deferred by ADR-0019; the index travels over HTTPS and every zip is pinned by its SHA-256); absolute zip URLs (a mirror would have to rewrite the index); a separate update-check switch (the existing update mode already expresses "no update traffic"); a sidebar badge for updates (not in scope; the cached check shows on the page at once).

**Interfaces and data.** Formats, codes and error keys: spec REQ-DATA-b40d3f9b. Settings `plugins.catalog?` (URL rule; the page sends the whole `plugins` object so index and proxy stay). Build input `VERA_PLUGIN_CATALOG_URL` -> `__VERA_PLUGIN_CATALOG_URL__` (validated like the update feed; empty by default). Channels: `plugins.catalog {refresh}` -> view; `plugins.catalogReview {id}` -> `{review: PluginReview (its `installed` names the installed version), id, version, tier, required}`; `plugins.catalogInstall {id, sha256}` -> installed summary. App event `plugins.catalog`. Store: `readPluginPackage(path)` (exported reader + examination + integrity hash) and `install(path, sha256?, origin?)` where `origin {tier, url}` records `tier` and `source {kind: catalog, path: url}`; `pluginInstalledSchema.source` gains `catalog`. The client keeps verified zips in `<userData>/plugins/catalog/` (temporary file + rename; removed on refusal and after install) and caches one view per location; a changed location re-reads. Errors: OFFLINE download, INVALID sha256/mismatch, CONFLICT downgrade/changed zip, NOT_FOUND unknown id; the renderer shows them through `ErrorMessage` with new keys.

**Files and test seams.** shared `plugin-catalog.ts` (+ `plugin-catalog.test.ts`), `program-rules.ts`, `plugins.ts`, `settings.ts`, `ipc.ts`, `events.ts`, `index.ts` (+ `plugins-ipc.test.ts`); core `plugins/store.ts` (+ `store.test.ts` origin), `plugins/catalog-source.ts` (+ `catalog-source.test.ts`, fixtures built in temp folders), `plugins/catalog.ts` (+ `catalog.test.ts` with a node:http loopback server and real `fetch`), `index.ts`; CLI `catalog.ts`, `args.ts`, `index.ts` (+ `tests/integration/cli.test.ts`); desktop main `catalog-checks.ts` (+ `catalog-checks.test.ts`, fake timers), `index.ts`, `electron.vite.config.ts`, `scripts/update-config.mjs` (`catalogUrl` build input, + `tests/packaging` case); renderer `plugin-catalog.tsx` (+ `plugin-catalog.test.ts`), `plugins.tsx`, `error-message.tsx`, `styles.css`, locales en/ro/de, `mocks/mockApi.ts` (+ `mockApi.test.ts`); e2e `plugins-catalog.spec.ts` (native: loopback catalog install, update with a changed rule opens review) and `plugins-mock.spec.ts` (catalog section in every language, theme, size); `05_Software/plugins/{packs.yaml,catalog.yaml,CONTRIBUTING.md,.ci/catalog.yml}`; `scripts/prepare-plugins.mjs` (+ test), `scripts/package.mjs`, `electron-builder.yml`, `.gitignore`, `package.json`.

**Risks and open decisions.** Security: without signing, whoever controls the catalog host or a company mirror controls what is offered; the review screen, tiers, SHA-256 pins against the index, the entry match and the downgrade refusal bound the damage, and HTTPS is required off loopback. TOCTOU between review and install: the kept zip is re-hashed against the entry and the package integrity hash is bound (existing CONFLICT). Concurrency: two reviews of one id write distinct temporary files and rename to the same content-addressed name. Open for the user: official catalog URL and hosting, the hosted repository's CI platform (the template targets GitHub-compatible Actions, which Gitea runs), the signing decision. Linux: native e2e and packaged offline install run only on Windows here.
