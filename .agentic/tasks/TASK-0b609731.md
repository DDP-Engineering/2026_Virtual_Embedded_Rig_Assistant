## Frame

Problem: opening a session validates the same data repeatedly on the critical path: `SessionHub.get` zod-parses every stored event although `record()` already parsed it at write time (OBSERVED `libraries/core/src/sessions/hub.ts:25,30`); `sanitizeSessionSnapshot` deep-copies the whole snapshot with `structuredClone` before scrubbing (OBSERVED `apps/desktop/src/main/events.ts:59`); the router validates the whole response (OBSERVED `main/ipc-router.ts:83`) and the renderer again (STATED #253). The chat and each mounted side tab (Changes, Artifacts, Plan) each run their own `useSessionEvents`, so with a side tab open a session is fetched, validated and held twice with two 2 s polls and focus listeners (OBSERVED `workspace.tsx:38`, `changes-tab.tsx:17`, `artifacts-tab.tsx:17`, `plan-tab.tsx:13`; STATED #253 Problem).
Desired outcome: each byte of a session read is validated once in main (response `safeParse`) and once at the renderer trust boundary; one session view (one `session.get`, one subscription, one poll) per window, shared by the chat and side tabs; the remaining validation cost is visible as `validateMs` in the opt-in probe (STATED #253 Goal, plan 4).
Actors: the user opening sessions and side tabs in the desktop renderer; the main IPC handler; the developer running `perf:sessions`.
Primary scenario: a 2,000-message session is open in the chat; the user opens the Changes tab; no second `session.get` is sent and the tab shows the same snapshot; a later live event updates both views from the one subscription.
Examples: `hub.get` on the existing fixtures returns the same snapshot with and without per-event parsing; a stored row edited to `{"type":"session.updated","title":42}` makes `session.get` return `INTERNAL` (response validation), not crash; a non-JSON row also gives `INTERNAL` (STATED #253 Tests).
Counterexamples: session export/import keeps per-event parsing (`service.exportSession`, OBSERVED `service.ts:235`): that data leaves or enters from outside (STATED #253 plan 1).
In scope: (a) `hub.get` uses `JSON.parse` + `foldSessionEvents` only; (b) `sanitizeSessionSnapshot` builds the scrubbed copy in one pass without `structuredClone`, same scrub rules; (c) a `SessionViewProvider` around the workspace and the right panel in `App.tsx`; chat and three tabs read it; `useSessionEvents` stays the implementation (reconcile, generation, PERF-04 frame batching unchanged); (d) `validateMs` in the main probe around the response `safeParse`, renderer equivalent if simple (STATED coordinator brief 3a-3d).
Out of scope: removing the main or renderer whole-response validation (STATED user decision 2026-11-14); subscription replay parsing in `hub.subscribe` (not named by #253; replay is short and validated again by `createEventEmitter`, OBSERVED `events.ts:215`); windowing (later epic child).
Constraints: no new dependency; Windows and Linux; no commit or push; targeted tests only; 1-2 review rounds, golden-path blockers only (STATED coordinator brief).
Success signals: core service test (same snapshot, corrupt row), router test (corrupt snapshot -> INTERNAL), events sanitize tests green unchanged; renderer test: opening the Changes tab with a session open sends no second `session.get`; hook/workspace/tab tests green apart from the known `Settings selects one page...` failure; tooling tests green; typecheck and biome clean; `perf05-after.json` compared with `perf03-after.json` (loadMs, mainHandlerMs, snapshotMs, ipcMs medians).
Evidence: OBSERVED reads of the files above; `aegis explain` for hub.ts/events.ts/use-session-events.ts lists REQ-FUNC-5e2438d5 (fold), REQ-FUNC-2b462360 (typed session IPC, router/events), REQ-REL-4bea0006 (renderer session streams), REQ-TEST-a14f8f9b (probe metrics).
Assumptions: INFERRED from `hub.get` building a fresh fold from freshly parsed rows that the snapshot passed to `sanitizeSessionSnapshot` is owned by the handler, so a shallow copy that replaces only scrubbed fields cannot leak unscrubbed strings or share state with another caller. Unknowns: renderer validation share on `large` (measured by `validateMs` if added); native Ubuntu timing (no host here, no platform-specific code).
