## Frame

Problem: Users get plugins only bundled with each VERA installer. The default catalog URL is empty, and the
remote `index.json` is not signed: ADR-0019 deferred signing (STATED, ticket PLG-07 #268; OBSERVED
`02_Tools/release/update-config.mjs` `pluginCatalogFeed`, core `catalog.ts` reads `index.json` without a signature).
Desired outcome: `npm run prepare:plugins` builds a catalog release into `07_Delivery/plugins/`. The release is a
plain folder that can be published, for example as Gitea release assets. It has two channel indexes: stable
(`>= 1.0.0`) and pre-release (all plugins). The indexes are signed at release with Ed25519, and the public key is
pinned in the VERA build. The client refuses an unsigned or wrongly signed remote index with an explicit state and
falls back to the bundled release, which is trusted through its installer. A Plugins page setting chooses the
channel (default stable). The release procedure is documented in `02_Tools` (STATED, ticket + coordinator
decisions 1-5).
Actors: the release maintainer, who builds, signs and uploads; the VERA user, who picks a channel and installs
from the remote catalog; mirror operators, who copy the folder.
Primary scenario: the maintainer runs prepare:plugins and `vera catalog sign`, then serves the folder over
http(s). The user sets the catalog URL, keeps the stable channel and sees ltspice only. The user switches to
pre-release and sees every plugin. A changed index shows "untrusted", and the bundled plugins stay listed.
Examples: stable lists `ltspice` 1.0.0 only; pre-release lists the 37 official plugins at their newest version
(OBSERVED: PLG-01 version table, only ltspice is 1.0.0). An index edited after signing gives problem `untrusted`.
An index without a `.sig` gives `unsigned`.
Counterexamples: the bundled release (`<resources>/plugins/`, or `07_Delivery/plugins/` in development) is
never signature-checked and lists every official plugin whatever the channel (STATED, coordinator decision 3).
In scope: channel indexes in `vera catalog build`; `vera catalog keygen` and `vera catalog sign`; verification
in core `PluginCatalog`; the channel setting (shared settings schema and the renderer Plugins page); the
public-key build input; the real key pair (private key outside the repository); release docs in `02_Tools`.
Out of scope: publishing, uploading or pushing; setting a default `VERA_PLUGIN_CATALOG_URL`; signing individual
zips (the plan's §5 non-goal; the signed index carries every zip's SHA-256); a compatibility path for unsigned
remote catalogs (STATED, coordinator decisions 4-5).
Constraints: no new dependency, Node `crypto` only (STATED, decision 1). Pre-release software: no compatibility
or migration code, `format: 1` stays (STATED). Must work on Windows and Linux. Files written from Python use
`newline="\n"`. Work happens on branch feature/261-plugin-management in the `_plg` worktree. No commit and no
push.
Success signals: PLG-07-A, a release folder installs from a local http mirror (the published-URL half stays
open until the user's go-ahead); PLG-07-B, a changed or unsigned index is refused with an explicit state while
the bundled release still works; PLG-07-C, pre-release shows 0.x plugins and stable only `>= 1.0.0`; PLG-07-D,
the procedure is documented in `02_Tools` and the 24 h check rhythm is unchanged.
Evidence: OBSERVED core `catalog.ts` (Snapshot, readIndex, bundled fallback), `catalog-source.ts`
`buildCatalogRelease`, desktop `catalog-checks.ts` (24 h), main `index.ts` `catalogLocation`,
`electron.vite.config.ts` define `__VERA_PLUGIN_CATALOG_URL__`, renderer `plugin-catalog.tsx` `CatalogUrl`, and
e2e `plugins-catalog.spec.ts` (loopback catalog host).
Assumptions: Gitea release assets are a flat list of files with no folders, served at
`/releases/download/<tag>/<name>` (INFERRED from Gitea's release download route).
Unknowns: the hosting URL; it must be https for `catalogUrl`, and the Gitea at `http://192.168.1.15:3001` is
plain http on the LAN, so it is not accepted as is (OBSERVED `catalogUrl` in shared `plugin-catalog.ts`; UNKNOWN
how the user will serve it).
Decision-blocking questions: none. The coordinator decisions 1-5 settle the key handling, the channels and

Proposed behaviors (accepted by the coordinator brief): the channel indexes are files in one flat folder,
`index-stable.json` and `index-pre-release.json`, each with a detached `<name>.sig` (base64 Ed25519). They are
not two folders, because release assets cannot hold folders. Remote reads use the selected channel's file and
signature. New view problems are `unsigned` and `untrusted`.

## Design

**Approach.** The release stays one flat folder. `buildCatalogRelease` writes `index.json`, as it does
today, plus the two channel indexes, filtered with shared `pluginMaturity` (REQ-DATA-78f62129). Signing is a
separate release step, `vera catalog sign`, because development builds have no private key; `vera catalog
keygen` creates the pair (REQ-SEC-daf01d33, REQ-SEC-bd56a6c0). Both commands live in core `catalog-source.ts`
and are wired through the CLI next to check and build: the ADR-0019 status names the CLI as the catalog's
release steps. The client in core `catalog.ts` reads `index-<channel>.json` and then its `.sig` from a remote
origin. It verifies with `crypto.verify(null, …)` against the pinned SPKI key before parsing
(REQ-SEC-3e11ffe4, REQ-SEC-d96c5192, REQ-FUNC-b7ff35bf). The bundled origin reads `index.json` with no
signature. The location key of the snapshot becomes `url + channel`, so a channel change reads again. I
rejected two index folders: release assets have no folders (see the frame DEVIATION).
**Interfaces and data.**
- Shared: `CATALOG_CHANNELS` / `catalogChannelSchema` (`stable`, `pre-release`) and `catalogChannelIndex(channel)`,
  which gives the file name. `pluginSettingsSchema.channel` is optional, and readers default it to stable. The
  view `problem` adds `unsigned` and `untrusted`.
- Core: `PluginCatalogOptions.channel?()` (default stable) and `publicKey?: string` (PEM). With no key, every
  remote index is `untrusted`. New exports: `catalogChannel(index, channel)`, `generateCatalogKeys(privatePath,
  publicPath)` (wx writes, mode 0600), `signCatalogRelease(folder, privatePem, publicPem?)`.
- CLI: `catalog keygen --private --public` and `catalog sign --release --key [--public]`, exit 0/1.
- Build: `pluginCatalogKey(path)` in `update-config.mjs` reads the PEM path from `VERA_PLUGIN_CATALOG_KEY`,
  default `02_Tools/release/catalog-signing-key.pub.pem`, and throws for a key that is not Ed25519 public
  (REQ-PLAT-dad138cf). `electron.vite.config.ts` defines `__VERA_PLUGIN_CATALOG_KEY__`. Main uses the
  `VERA_TEST_CATALOG_KEY` env (PEM text) in test builds only, like `VERA_TEST_BUNDLED_PLUGINS`, so e2e can pin
  a throwaway key.
- Renderer: `CatalogChannel` select in the catalog settings `<details>` saves `plugins.channel`, keeping the
  other plugin settings, the same as `CatalogUrl`, and invalidates the catalog query. It adds problem messages
  (REQ-UX-84d8cad7) in en/ro/de.
**Files and test seams.** Shared `plugin-catalog.ts` and `settings.ts` (plugins-ipc test); core `catalog-source.ts`
(catalog-source test: channels, keygen, sign) and `catalog.ts` (catalog test: channel and signature states,
loopback host); CLI `args.ts` and `catalog.ts` (cli integration test); `update-config.mjs` and
`electron.vite.config.ts` (packaging updates test); main `index.ts`; renderer `plugin-catalog.tsx`
(plugin-catalog test); e2e `plugins-catalog.spec.ts` (signed loopback release); prepare-plugins packaging test
(ltspice is the only stable plugin). Docs: `02_Tools/release/catalog-release.md`, linked from `02_Tools/README.md`,
and `07_Delivery/README.md`.
**Risks and open decisions.** Security: the private key never enters a repository, a log or a test. Tests use
pairs generated in the test. Hosting must be https (`catalogUrl`); the LAN Gitea is plain http, which is open for
the user. A stable plugin that requires a 0.x plugin is left without it in the stable channel; this is accepted
(today only ltspice is stable, and it requires nothing). Publishing stays open.
**Requirement map.** REQ-DATA-78f62129: build channels. REQ-SEC-daf01d33 and REQ-SEC-bd56a6c0: CLI sign and
keygen. REQ-SEC-3e11ffe4 and REQ-SEC-d96c5192: client verify. REQ-FUNC-b7ff35bf: channel file and snapshot key.
REQ-UX-84d8cad7: renderer. REQ-PLAT-dad138cf: build key input. REQ-FUNC-98ded47a: no design impact beyond the
signed fixture. REQ-FUNC-ce542246: no design impact.
**Diagrams.** DEVIATION design: no diagrams. The flow is one linear read, then verify, then parse, which the
Approach states.
