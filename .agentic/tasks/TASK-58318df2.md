## Frame

Problem:
- OBSERVED: text before the first heading of an HTML, docx or odt file becomes a
  section with slug "" (core knowledge/extraction.ts `extractHtml`; office.ts maps
  docx/odt through it). A Word file without heading styles is one such section in
  full. Titled sections always get a non-empty slug, since `slugger()` falls back to
  "section", so only the untitled leading section is affected.
- OBSERVED: for that section `documentRef` (search.ts) and `read` return the bare
  path as ref, because only Markdown has a line-range fallback. `parseRef`
  (shared refs.ts) cannot parse a bare path: the heading grammar needs a non-empty
  `[\p{L}\p{N}_-]+` slug. The agent therefore cannot cite those hits,
  `validDocumentRef` rejects them, and the Docs-tab search
  (`WorkbenchService.searchDocuments`) drops them.
- OBSERVED: `read` throws "Heading exceeds output budget" for any section over
  12000 characters (or 28000 JSON characters). HTML, document and spreadsheet kinds
  have no line or page locator to fall back on, so a long chapter, a headingless
  Word file or a large sheet cannot be read at all through read_doc. Markdown sections
  have the same limit but can be read by lines.
- STATED (round-1 reviews of TASK-ca6e05a5, carried here by the user's "Do this task
  here"): both gaps were deferred from office extraction as a follow-up.
Desired outcome:
- Every search hit and read_doc result for HTML, document and spreadsheet sources
  carries a ref that parses, validates as a citation, opens the viewer at that
  section and shows a chip, including the untitled leading section.
- read_doc can return any section in full through a bounded sequence of reads, each
  within the existing 12000-character / 28000-JSON budget, and says when more remains.
Actors: the agent (search_docs, read_doc, citations), the user (citation chips,
  Docs-tab search, document viewer).
Primary scenario: a headingless Word file of 30000 characters is indexed. The agent
  searches a phrase in it, gets a citable ref, reads the whole section in successive
  parts, answers citing it, and the user opens the chip and lands at the section.
Examples:
- `docs/notes.docx` with no heading styles: today search_docs returns ref
  `docs/notes.docx`, which cannot be cited; afterwards a ref that parses and validates.
- `docs/report.xlsx` sheet "Timing" with 40000 characters of rows: today
  `read_doc {heading: "timing"}` throws; afterwards it is readable in parts.
Counterexamples:
- Markdown preamble: already cited by line range (`#L1-L3`); it stays that way.
- PDF pages and presentation slides: page refs, unaffected.
- A titled section under 12000 characters: one read, unchanged ref and output.
In scope: the ref for the untitled leading section of HTML/document sources (and any
  section kind that can have it); bounded part reads of oversized sections for every
  section kind; search_docs refs, read_doc, citation validation, viewer anchoring,
  Docs-tab search results, chip label; tests; component knowledge pages.
Out of scope: changing slugs of titled sections; new locators for PDF/presentation;
  splitting sections at index time; legacy .doc/.ppt/.xls (parent RULING-003 of
  TASK-581e6591).

## Design

**Approach.**
- Grammar (REQ-FUNC-626d3017): shared refs.ts lets the heading slug be empty, `#h=` →
  `{kind: "heading", slug: ""}`; formatRef accepts "" and referenceLabel gives
  "<file> #start". Paths still go through `valid()`, so a bare path stays unparseable.
  Rejected: a reserved or generated slug (RULING-001).
- Issuing (REQ-FUNC-2a51bc39): search.ts `documentRef` keeps heading refs for titled
  sections and Markdown line ranges (only Markdown locators carry start/end, chunk.ts),
  and otherwise formats `#h=` instead of the bare path. `read` returns `#h=` for an
  untitled section of a non-Markdown source.
- Validation (REQ-FUNC-845e3114): `validDocumentRef` already checks section kinds and
  slug membership; it adds that an empty slug needs a non-Markdown section kind, so
  Markdown preambles stay cited by lines.
- Docs search (REQ-FUNC-73136b97): `currentBounds` already lists every slug, including "";
  the hits now parse, so `WorkbenchService.searchDocuments` keeps them with no change
  beyond tests.
- Viewer (REQ-UX-9be5fd96): viewer.ts treats the anchor as present when it is not null
  (today "" is skipped as falsy) and checks it exists; the renderer effect focuses the
  section when `anchor !== null`, matching `data-heading=""`.
- Parts (REQ-FUNC-3b70651a, REQ-FUNC-91405ce5): readDocSchema gains `part`
  (int, optional). Heading reads split `section.text` into consecutive substrings, each
  fitting the existing budget (12000 characters and 28000 JSON characters, as `bounded`).
  A part ends after the last newline that fits; a line that alone exceeds the budget is
  cut at the largest fitting length, never inside a surrogate pair. The substrings
  concatenate exactly to the section text. Every heading read returns
  `{path, text, truncated, part, parts, ref}`; the old "Heading exceeds output budget"
  error goes away. `part` < 1, `part` > parts, `part` with page/line arguments, or `part`
  on a PDF/presentation/text source is an Error that names the range or the heading
  locator. Rejected: part-suffixed refs (RULING-002).

**Interfaces and data.**
- Ref grammar: `path#h=` added; every existing ref keeps its parse and format.
- read_doc args: `part?: integer`; heading results add `part` and `parts`. The tool
  description names `heading: ""` for the start of a document and `part` for long
  sections.
- No storage, cache or extraction change: the empty slug is already persisted.

**Files and test seams.**
- shared/src/refs.ts + refs.test.ts (REQ-FUNC-626d3017).
- core knowledge/search.ts + search.test.ts (REQ-FUNC-2a51bc39, -845e3114, -3b70651a,
  -91405ce5); tools/documents.ts description.
- core knowledge/viewer.ts + viewer.test.ts; workbench/service.ts test in
  service.test.ts (REQ-FUNC-73136b97, REQ-UX-9be5fd96).
- renderer documents/viewer-context.tsx + documents.test.ts, mock documents
  (REQ-UX-9be5fd96); native e2e: office-documents.spec.ts gains a headingless docx and
  a `#h=` citation through a replay script.

**Risks and open decisions.**
- Compatibility: refs persisted before this task never contained `#h=`, so earlier
  citations keep their parse; no migration.
- A model may emit `#h=` for Markdown; it is invalid unless issued, as today.
- No open product decisions.
