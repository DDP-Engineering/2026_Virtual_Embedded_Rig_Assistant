## Frame

Problem: plugins can be installed, enabled, classified and approved (PLG-01..03), but the agent cannot see or run any program: no `run_program`/`program_output`/`program_stop` tool exists, the system prompt has no program list, plugin skills are invisible to `SkillCatalog`, and nothing composes find -> prepare -> gate -> re-prepare -> consume -> runner (OBSERVED: `core/src/tools/registry.ts` builtin list, `agent/prompt.ts`, `skills/catalog.ts` sources workbench|user, knowledge/plugins.md "no agent tool prepares or runs programs yet"). PLG-03 left limits for this package: Windows drive-relative arguments (`C:build/app.bin`) and alias spellings (`app.bin::$DATA.`) are not bound to the approval's hashes, a named file can change between consume and spawn, and its e2e ran on the browser mock (OBSERVED: TASK-9b39247f State `issues`; handover note). A Linux file whose name the guard reserves (`aux.bin`) is also unbound (OBSERVED: same State line).
Desired outcome: the agent sees enabled programs in a `<programs>` prompt block with the run rule, loads plugin skills through `load_skill`, runs declared programs with `run_program` (foreground result or background handle) under the risk rules and approvals, reads background output with `program_output` (`waitMs`, `until`) and stops runs with `program_stop`; session stop aborts runs; the CLI prints the same events; and the files an approval hashed are the files that run, including Windows aliases and drive-relative spellings (STATED: ticket #60 scope and done-when; task brief section 2).

## Design

**Approach**
- New core module `plugins/program-tools.ts` owns the agent side: the `ProgramResolver` port (`resolve(plugin, program, signal)` -> `{executable, prefix?}` or undefined), `ProgramHost {runner, clock, plugins(), resolver}`, a per-session `ProgramSession` handle registry, the tools `run_program` (class `program`, with `prepare`), `program_output` and `program_stop` (class read), `programPromptEntries(host, skills)`, `programTimeout(...)` and a bounded `until` matcher. Desktop main and the CLI compose the host; core never resolves install kinds (PLG-05) (REQ-FUNC-29dd2b92, REQ-FUNC-59308834).
- Primary flow, reusing the write-tool seam: the runtime sends class `program` through `host.approve` like `write` and never batches it (REQ-FUNC-29dd2b92). `SessionService.approve` calls `registry.prepare` with per-call ids: `run_program.prepare` = `plugins()` -> `findProgram` -> refuse a `launcher` or unresolved program (REQ-SEC-affac265) -> `prepareProgramRequest`. `run_program.prepare` turns a `refuse` policy into an error naming risk and mode (REQ-SEC-08f730b3); the service then refuses credentials with `host.scrub` (REQ-SEC-b9d4244f) and asks `ApprovalGate.request` (or a host PermissionEngine, whose allowed request must equal the re-prepared one). The execute branch calls `apply`: prepare again from current plugins, resolver and files, `ctx.programs.consume` (gate CONFLICT), then `runner.start` with `beforeSpawn` re-hashing the approved files (REQ-SEC-c730711e, REQ-SEC-370f2d9b); foreground waits for `done` (REQ-FUNC-bce7d786), background registers the run (REQ-FUNC-9b38f5a8). Results pass `capToolResult` and `host.scrub`.
- Rejected: resolving `find` programs now (PLG-05 owns install kinds); copying approved files to a private snapshot to close TOCTOU entirely (programs would see other paths; idf.py reads project files relative to cwd); a worker for `until` (node:vm `timeout` interrupts V8 regex backtracking, observed in frame).

**Interfaces and data**
- `run_program {program, args: string[] = [], cwd?, timeout? 1..3600 s, background?}`. Command line = resolver prefix, manifest prefix with `${pluginDir}` = plugin folder, agent args; env values with `${workbench}`/`${pluginDir}` replaced (REQ-FUNC-8e22989a). Timeout cap = largest `timeout` of matching rules (new `classification.timeout` in shared `classifyCommand`), else the program's, else 600 s; foreground default = cap, background none unless given; agent values clamp (REQ-FUNC-90a95bef). Foreground result `{exitCode, durationMs, risk, output, truncated, log}` plus `timedOut`, `stopped` or `error` when set; background `{handle, risk, log}`.
- `program_output {handle, waitMs? 0..30000 = 0, until? 1..512}` -> `{output, truncated, running, exitCode?, matched?}`: polls `run.read()` every 50 ms through `host.clock.sleep`, gathering at most 12 000 characters, until the run ends, `until` matches or waitMs passes (REQ-FUNC-e54f89a4, REQ-FUNC-da3adc80). `until` compiles once (invalid -> error) and each test runs in `vm` with a 100 ms timeout (timeout -> error) (REQ-SEC-e9bc4628).
- `program_stop {handle}` -> `{exitCode, stopped, timedOut, durationMs, output, truncated, log}`; the handle leaves the registry (REQ-FUNC-b70bb17e). Unknown or foreign handles -> error (REQ-FUNC-c6761a12). The registry keeps at most 32 handles, dropping the oldest finished.
- Errors reach the model as messages: undeclared, ambiguous, not available, argument refusals with index (count, length, control, argument-file, stream, unbound), refused (risk, mode), changed after approval, BUSY limit or port with handle, DENIED cwd.
- `SessionService.stop(id)` also calls `runner.stopSession(id)`; desktop main drops its duplicate call (REQ-FUNC-ea2dfb26).
- Prompt: `SystemPromptInput.programs?: {name, version|null, plugin, description, skills[]}[]`; block `<programs>` after `<skills>`, line `- <name>[ <version>] (plugin <id>): <description>[ Skill: a.| Skills: a, b.]`; the run rule joins Rules only with entries (REQ-FUNC-48cc01a9). Entries: enabled issue-free plugins in id order, programs in name order, resolved and without launcher, version from install.json, the plugin's enabled listed skills (REQ-FUNC-fa6222a5).
- Skills: `skillSourceSchema` adds `plugin`, `skillSummarySchema.plugin?`; `skillTargetSchema` takes only workbench/user (REQ-SEC-f7e4f258). `SkillCatalog` option `plugins()` -> `{id, folder}[]`; plugin roots are `<folder>`, names resolve workbench > user > plugins by id (REQ-FUNC-6d88d2ec, REQ-FUNC-a5eff6c9). `WorkbenchService.loadPlugins(id)` loads the enabled, issue-free plugins and feeds both the catalog and the program host.
- Binding (`program-request.ts`, `platform` input defaulting to `process.platform`): Windows drive-relative `X:rest` -> cwd-relative on the cwd's drive, else `X:\rest` (REQ-SEC-0e45a496); per-segment loop stripping trailing dots/spaces, `::$DATA`, `::$INDEX_ALLOCATION`, `:$I30:$INDEX_ALLOCATION` (REQ-SEC-13954028); a remaining `:` in a segment whose base exists -> DENIED stream (REQ-SEC-43a0b743); off Windows an existing workbench file the guard reserves -> DENIED unbound (REQ-SEC-aaeae5cb). `verifyProgramFiles(request, signal)` re-hashes for `beforeSpawn`.
- Runner: `RunRequest.beforeSpawn?()` awaited after the log opens and right before `host.spawn`; a throw abandons the run (REQ-SEC-370f2d9b).
- Instrumented desktop builds read `VERA_TEST_PROGRAMS` (JSON `{"<plugin>/<program>": {executable, prefix?}}`); production desktop and CLI resolve nothing until PLG-05 (REQ-FUNC-83ad0f58).

**Risks and open decisions**
- Residual TOCTOU: a program opens its files after it starts; Node cannot hold share-deny handles on Windows. The agent's own tools run one at a time during a run, so only the user, another session or a background run can write in that window; the knowledge page states the limit.
- `until` blocks the main thread at most 100 ms per attempt, and the first timeout ends the call.
- Drive-relative binding relies on the minimal environment carrying no `=X:` variables; a runner test pins that.
- DEVIATION design: production resolves no executable until PLG-05, so the CLI cannot run a real program yet; the CLI test proves composition and events, and real runs are proven in core replay tests (scripted host) and the native e2e (instrumented resolver).
- No format version changes; plan.md and architecture.md gain the resolver seam, the timeout default and the new refusals.
